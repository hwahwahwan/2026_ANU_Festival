# 학교 축제 QR 주문 웹서비스 전체 요약

> v0.10 · 2026-09-18

QR로 메뉴를 주문하고 계좌이체 후 부스에서 입금 확인을 받는 모바일 웹서비스다.

고객은 QR을 통해 주문하고 웹에서 주문 상태를 확인하며, 운영자는 주문·메뉴·계좌·매출을 관리한다.

## 서비스 흐름

QR 첫 화면은 다음 두 기능만 제공한다.

```text
주문하기
주문 확인
```

### 주문하기

```text
QR 접속
  ↓
메뉴 선택
  ↓
이름 + 전화번호 입력
  ↓
주문 생성
  ↓
주문번호 발급
  ↓
계좌이체
  ↓
운영자 입금 확인
  ↓
제조
  ↓
준비 완료
  ↓
고객 수령
```

Cookie로 고객을 식별하지 않는다. 이름·전화번호는 주문 생성 요청에 직접 담아 `orders` 테이블에 저장한다.

### 주문 확인

```text
이름 + 주문번호
```

를 이용하여 해당 주문 1건만 조회한다 (`POST /orders/lookup`).

새로고침 시 재입력이 필요 없는 것은 프론트엔드 localStorage가 이름+주문번호를 기억해두기 때문이며, 서버는 별도 세션이나 Cookie로 고객을 기억하지 않는다.

lookup 성공을 이유로 과거 주문 전체 접근을 복구하지 않는다.

## 주문 상태

```text
PAYMENT_PENDING
      ↓
ACCEPTED
      ↓
COOKING
      ↓
READY
      ↓
COMPLETED
```

미입금 취소는 다음과 같다.

```text
PAYMENT_PENDING → CANCELLED
```

| 상태 | 의미 |
| --- | --- |
| PAYMENT_PENDING | 입금 확인 대기 |
| ACCEPTED | 입금 확인 및 주문 접수 |
| COOKING | 제조 중 |
| READY | 준비 완료 |
| COMPLETED | 수령 완료 |
| CANCELLED | 미입금 주문 취소 |

미입금 주문은 자동 삭제하거나 자동 취소하지 않는다.

## 백엔드 기술 스택

| 영역 | 기술 |
| --- | --- |
| Framework | NestJS |
| Language | TypeScript |
| API | REST API |
| Realtime | Socket.IO |
| Database | PostgreSQL |
| DB Driver | pg(node-postgres) |
| Admin Auth | JWT + HttpOnly Cookie |
| Config | NestJS ConfigModule |
| Server | Oracle Cloud Free Tier Ubuntu |
| Transport | HTTPS |
| Deployment | 단일 NestJS 프로세스 우선 |

Backend는 ORM을 사용하지 않고 PostgreSQL에 `pg`로 직접 접근한다.

## 역할 분리

### Backend 1 — 주문·결제

주문의 전체 생명주기를 담당한다.

```text
Order
OrderItem
OrderHistory
Refund
OrderDailyCounter
고객 식별(이름+전화번호)
이름+주문번호 조회
주문번호
멱등성
동시성
주문 Transaction
관리자 주문 처리
```

소유 테이블:

```text
orders
order_items
order_history
order_refunds
order_daily_counters
```

관리자 페이지에서 호출하는 기능이어도 Order를 변경하는 API라면 Backend 1 담당이다.

예:

```text
입금 확인
제조 시작
준비 완료
수령 완료
취소
환불
주문 이력
```

---

### Backend 2 — 운영·실시간

운영 기능과 실시간 통신 및 배포를 담당한다.

```text
AdminAuth
Menu
PaymentSettings
Sales
Realtime
Socket.IO
Infra
Deploy
```

소유 테이블:

```text
admins
menus
payment_settings
```

Sales는 Backend 1 주문 테이블을 읽을 수 있지만 수정하지 않는다.

Realtime 역시 주문 이벤트를 전달할 뿐 주문 상태를 직접 변경하지 않는다.

## 도메인 간 연결

```text
Backend 1
Order 변경
    ↓
PostgreSQL COMMIT
    ↓
order.created / order.updated
    ↓
Backend 2 Realtime
    ↓
Socket.IO
    ↓
고객 / 관리자
```

PostgreSQL이 최종 상태의 기준이다.

Socket.IO 이벤트는 변경 알림 역할만 하며 클라이언트는 필요하면 REST로 최신 데이터를 다시 조회한다.

## 확정된 핵심 정책

| 영역 | 정책 |
| --- | --- |
| 고객 | Cookie 없음 — 이름+전화번호(주문 생성) |
| 주문 복구 | 이름 + 주문번호로 1건만 조회 |
| 관리자 인증 | JWT HttpOnly Cookie |
| 관리자 JWT | 30분 만료, Refresh 없음 |
| 매출 보호 | 매출 조회마다 현재 관리자 PW 재입력 |
| 주문번호 | `MMDD-XXXX` |
| 가격 | 주문 제출 시 서버 DB 가격이 최종 가격 |
| 메뉴 | 가격·판매/품절만 수정 |
| 자동 재고 | 사용하지 않음 |
| 주문 중복 방지 | orderRequestId + UNIQUE + Transaction |
| 계좌 | DB 현재 부스 계좌 사용 |
| 매출 기준 | Asia/Seoul + payment_confirmed_at |
| 실시간 | Socket.IO |
| 상태 복구 | REST 최신 조회 |
| 외부 알림 | 사용하지 않음 |
| 배포 | Oracle Ubuntu 한 서버 + HTTPS |

## 주문 이력과 환불

주문의 이전 데이터는 삭제하거나 덮어쓰지 않는다.

다음 처리를 모두 `order_history`에 기록한다.

```text
주문 생성
입금 확인
제조 시작
준비 완료
수령 완료
취소
환불
```

입금 확인 이후 다음 상태에서는 환불 처리가 가능하다.

```text
ACCEPTED
COOKING
READY
COMPLETED
```

환불 시에도 다음 원본은 유지한다.

```text
원 주문
원 주문 항목
원 결제금액
payment_confirmed_at
```

환불 기록은 별도로 추가한다.

## 현재 제외

MVP에서는 다음 기능을 구현하지 않는다.

```text
Prisma
Redis
Kafka
RabbitMQ

온라인 PG
자동 입금 확인 API

고객 회원가입
학번 인증
pickupCode

자동 재고 수량 관리
미입금 자동 삭제

SMS
Web Push
카카오 알림

PushSubscription
Service Worker 기반 알림

매출 전용 JWT
매출 권한 유지 세션
```

v0.9부터 주문 생성 시 전화번호를 입력받지만, 이는 SMS·알림 발송용이 아니라 주문을 찾아가지 않을 때 연락하기 위한 연락처일 뿐이다. 위 제외 목록(SMS, Web Push, 카카오 알림)은 그대로 유지된다.

향후 포트폴리오 확장으로 TossPayments 테스트 결제를 추가할 경우 Payment 도메인은 Backend 1이 담당한다.
