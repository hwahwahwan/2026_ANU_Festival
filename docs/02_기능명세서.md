# 0. 서비스 범위

학교 축제 기간에 QR로 메뉴를 주문하고, 계좌이체 후 부스에서 관리자가 입금을 직접 확인하는 소규모 MVP 서비스다.

고객은 회원가입/로그인을 하지 않으며, Guest 계정이나 고객 Cookie/Session도 사용하지 않는다. 관리자만 ID/Password로 로그인한다.

# 1. 고객 기능

## 1-1. 메뉴 조회

**설명**

고객이 현재 판매 중인 메뉴와 가격, 품절 여부를 확인한다.

**동작 흐름**

1. 고객이 QR로 접속해 "주문하기"를 선택한다.
2. 프론트엔드가 메뉴 목록을 조회한다.
3. 메뉴명, 현재 가격, 판매중/품절 여부를 화면에 표시한다.

**주요 규칙**

- 메뉴 종류는 미리 정해져 있다. 추가/삭제 기능은 없다.
- 화면에 표시되는 가격은 참고용이다. 최종 가격은 주문 생성 시 서버가 다시 계산한다.

**예외 상황**

- 조회 실패 시 재시도 안내를 표시한다.

**관련 API**

- `GET /menus`

---

## 1-2. 메뉴 선택 및 수량 지정

**설명**

고객이 주문할 메뉴와 수량을 고른다.

**동작 흐름**

1. 메뉴 목록에서 원하는 메뉴의 수량을 늘리거나 줄인다.
2. 선택 내역과 예상 총액을 화면에 표시한다.

**주요 규칙**

- 품절 메뉴는 선택할 수 없다.
- 수량은 1 이상의 정수만 허용한다. 빈 주문(항목 0개)은 제출할 수 없다.
- 재고 개수나 자동 잔여 수량은 표시하지 않는다(자동 재고 관리 없음).

**예외 상황**

- 0 이하 수량 입력은 프론트엔드에서 차단한다. 서버도 동일하게 검증한다.

**관련 API**

- 없음 (프론트엔드 로컬 상태로만 관리되며, 제출 시점에 `POST /orders`로 전달)

## 1-3. 주문 정보 입력 (이름 + 전화번호)

**설명**

고객 식별을 위한 별도 계정이나 로그인 없이, 주문을 제출할 때 이름과 전화번호를 직접 입력한다.

**동작 흐름**

1. 메뉴·수량 선택을 마친다.
2. 이름과 전화번호를 입력한다.
3. 주문 생성 요청에 이 값을 그대로 담아 보낸다.

**주요 규칙**

- 이름은 UNIQUE가 아니다. 동명이인이 각각 별도 주문을 생성할 수 있다.
- 전화번호는 로그인/인증 수단이 아니라, 주문 미수령이나 문제 발생 시 관리자가 연락하기 위한 연락처다.
- 이름·전화번호는 이 입력값 자체가 저장되는 원본이며, 별도로 검증된 "진짜 값"이 따로 존재하지 않는다.

**예외 상황**

- 이름 길이 초과, 전화번호 형식 오류 등은 입력 검증 오류로 처리한다.

**관련 API**

- `POST /orders` (요청 필드 중 일부)

---

## 1-4. 주문 생성

**설명**

고객이 선택한 메뉴·수량과 입력한 이름·전화번호로 실제 주문을 생성한다.

**동작 흐름**

1. 프론트엔드가 주문 시도 1회당 UUID(`orderRequestId`)를 생성한다.
2. 이름, 전화번호, 항목(메뉴ID+수량), `orderRequestId`를 담아 주문을 요청한다.
3. 서버가 메뉴의 현재 가격과 판매 가능 여부를 다시 확인한다.
4. 서버가 최종 총액을 계산하고 주문번호를 발급한다.
5. 주문·주문 항목·이력을 저장하고 응답으로 주문 상세를 반환한다.

**주요 규칙**

- 클라이언트가 보낸 가격·총액은 신뢰하지 않는다. 서버가 DB의 현재 가격으로 계산한다.
- 같은 `orderRequestId`로 같은 내용을 다시 보내면 새 주문을 만들지 않고 기존 주문을 그대로 반환한다(멱등성).
- 같은 `orderRequestId`로 다른 내용을 보내면 오류로 거절한다.
- 주문 시점의 메뉴명·가격을 스냅샷으로 저장한다. 이후 메뉴 가격이 바뀌어도 과거 주문 금액은 변하지 않는다.

**예외 상황**

- 품절 메뉴 포함 → `MENU_UNAVAILABLE`
- 같은 요청ID·다른 내용 → `IDEMPOTENCY_CONFLICT`
- 입력값 오류 → `VALIDATION_ERROR`

**관련 API**

- `POST /orders`

## 1-5. 주문번호 발급

**설명**

주문 생성이 성공하면 고객이 부스에서 제시할 고유 주문번호를 발급한다.

**동작 흐름**

1. 서버가 KST(Asia/Seoul) 기준 당일 날짜의 카운터를 원자적으로 1 증가시킨다.
2. `MMDD-XXXX` 형식(예: `0918-0042`)의 번호를 만든다.

**주요 규칙**

- `COUNT(*) + 1` 방식이 아니라 별도의 일별 카운터로 관리해 동시 요청에도 중복이 생기지 않게 한다.
- 번호가 연속적일 필요는 없다. 중복되지 않는 것만 보장한다.
- 날짜 판단은 서버 OS 시간대가 아니라 명시적인 Asia/Seoul 기준이다.

**예외 상황**

- 하루 9999건을 초과하면(발생 가능성은 매우 낮음) 새 주문 생성을 오류로 거절한다(`DAILY_ORDER_LIMIT_EXCEEDED`). 자동으로 자릿수를 늘리거나 다음 구간으로 넘어가지 않는다.

**관련 API**

- `POST /orders` (응답 필드)

---

## 1-6. 입금 계좌 확인

**설명**

고객이 계좌이체할 부스의 현재 입금 계좌 정보를 확인한다.

**동작 흐름**

1. 주문 생성 응답 또는 별도 조회로 은행명·계좌번호·예금주를 가져온다.
2. 화면에 표시하고 계좌번호 복사 기능을 제공한다.

**주요 규칙**

- 계좌 정보를 프론트엔드 코드에 하드코딩하지 않는다. 항상 서버(DB) 현재값을 조회한다.
- 주문별 계좌 스냅샷은 없다. 계좌가 바뀌면 과거 미입금 주문에도 새 계좌가 표시된다.

**예외 상황**

- 조회 실패 시 재시도 안내.

**관련 API**

- `GET /settings/payment`

---

## 1-7. 기존 주문 조회 (이름 + 주문번호)

**설명**

고객이 이전에 생성한 주문 한 건을 다시 확인한다.

**동작 흐름**

1. 이름과 주문번호를 입력(또는 localStorage에서 자동 채움)한다.
2. 서버가 이름+주문번호가 모두 일치하는 주문을 찾는다.
3. 일치하는 주문 1건을 반환한다.

**주요 규칙**

- 이름만 맞고 주문번호가 틀리면(또는 반대) 조회되지 않는다.
- 이름만으로 고객의 전체 주문 내역을 반환하지 않는다. 항상 "이름+주문번호" 쌍으로 1건만 조회한다.
- 로그인 세션이 없으므로 `GET /orders/me` 같은 "내 주문 목록 전체 조회" API는 존재하지 않는다.

**예외 상황**

- 불일치 시 `ORDER_NOT_FOUND`.

**관련 API**

- `POST /orders/lookup`

---

## 1-8. 주문 상태 확인

**설명**

고객이 자신의 주문이 현재 어느 단계인지 실시간에 가깝게, 또는 재조회로 확인한다.

**동작 흐름**

1. 주문 상세 화면에서 Socket.IO에 연결하고 이름+주문번호를 제시해 해당 주문 room에 참여한다.
2. `order.updated` 이벤트를 받으면 저장해둔 이름+주문번호로 다시 조회해 최신 상태를 반영한다.
3. 페이지 재진입, 소켓 재연결 시에도 동일하게 재조회한다.

**주요 규칙**

- PostgreSQL이 최종 상태의 기준이다. Socket.IO는 "바뀌었다"는 알림 역할만 한다.
- Socket room 참여도 `orderId`만으로는 허용되지 않는다. 이름+주문번호를 함께 제시해야 한다(REST lookup과 동일한 신뢰 수준).
- Socket 이벤트가 누락되어도 재조회로 상태가 복구된다.

**예외 상황**

- 소켓 연결 끊김 → REST 재조회로 복구.

**관련 API**

- `POST /orders/lookup`
- Socket 이벤트 `order.updated` (`03_API명세서.md` 실시간 이벤트 명세 참고)

## 1-9. 최근 주문 localStorage 활용

**설명**

여러 번 주문한 고객이 매번 이름·주문번호를 입력하지 않도록 브라우저에 최근 주문을 기억해둔다.

**동작 흐름**

1. 주문 생성/조회에 성공하면 `{customerName, orderNumber, savedAt}`을 localStorage 목록에 추가한다.
2. "주문 확인" 진입 시 저장된 목록을 읽어 각 항목을 개별적으로 다시 조회한다.

**주요 규칙**

- localStorage는 **인증 수단이 아니다.** 서버는 이 값을 신뢰하지 않고 매번 이름+주문번호로 재검증한다.
- 기기·브라우저별로 별도 저장되며 서버로 동기화되지 않는다.
- 값이 삭제되면 고객이 이름·주문번호를 직접 다시 입력해야 한다.
- 이미 저장된 것과 같은 `{customerName, orderNumber}` 조합이 다시 저장되면 중복 추가하지 않고 `savedAt`만 갱신해 목록 맨 앞으로 옮긴다.
- 목록은 `savedAt` 최신순으로 표시한다.

**예외 상황**

- 저장된 항목이 서버에서 더 이상 조회되지 않으면(보관 기간 만료 등) 그 항목만 조용히 목록에서 제외한다.

**관련 API**

- `POST /orders/lookup`

**localStorage 구조 (확정)**

- Key: `"anu-festival:recent-orders"`
- Value: `{ customerName: string, orderNumber: string, savedAt: string(ISO 8601) }[]`

# 2. 관리자 기능

## 2-1. 관리자 로그인

**설명**

ID/Password로 로그인해 관리자 전용 기능에 접근할 수 있는 인증 상태를 만든다.

**동작 흐름**

1. 관리자가 username/password를 입력한다.
2. 서버가 `admins` 테이블에서 계정을 조회하고 password_hash를 검증한다.
3. 성공하면 JWT를 발급해 HttpOnly Cookie로 내려준다.

**주요 규칙**

- 비밀번호는 해시(Argon2id 또는 bcrypt 중 택1)로만 저장한다. 원문 저장 금지.
- JWT 유효기간은 30분이며 Refresh Token은 사용하지 않는다.
- JWT Payload는 최소 정보(`sub` = admins.id)만 담는다.

**예외 상황**

- ID가 없거나 비밀번호가 틀린 경우 구분 없이 동일한 `ADMIN_LOGIN_FAILED` 오류로 응답한다(계정 존재 여부 노출 방지).

**관련 API**

- `POST /admin/auth/login`

---

## 2-2. 로그아웃

**설명**

관리자 세션을 종료한다.

**동작 흐름**

1. 로그아웃 요청 시 서버가 관리자 Cookie를 삭제한다.
2. 프론트엔드가 관리자 데이터와 소켓 구독을 정리하고 로그인 화면으로 이동한다.

**주요 규칙**

- 발급 시 사용한 Cookie 옵션(Domain/Path/SameSite/Secure)과 동일한 옵션으로 삭제한다.
- 현재 연결된 관리자 Socket도 함께 종료한다.
- JWT 자체의 서버 측 블랙리스트는 구현하지 않는다(만료 전 탈취 시 즉시 무효화는 안 됨 — 알려진 제약).

**예외 상황**

- 없음.

**관련 API**

- `POST /admin/auth/logout`

---

## 2-3. 주문 목록 조회

**설명**

관리자가 현재 접수된 주문들을 확인한다.

**동작 흐름**

1. 관리자 인증 확인 후 주문 목록을 조회한다.
2. 신규 주문은 Socket.IO `order.created` 이벤트를 받아 새로고침 없이 목록에 반영한다.

**주요 규칙**

- 관리자 전용 API이지만 주문 데이터를 다루므로 Backend 1(주문 도메인) 소유다.
- 정렬은 **최신 생성순 고정**이다(나중에 들어온 주문이 위로 올라온다). 별도 정렬 옵션은 없다.
- 페이지네이션은 모바일 환경을 고려해 **커서 기반**으로 한다(끝없이 스크롤/더보기하는 방식에 적합).
- 검색/상태 필터는 MVP에서 제공하지 않는다(전체 목록만).
- 이 목록 응답에는 `customerPhone`이 포함된다 — 관리자가 미수령 고객에게 연락할 때 필요하기 때문이다. 반면 고객이 직접 보는 주문 조회 응답(`POST /orders`, `POST /orders/lookup`)에는 전화번호가 포함되지 않는다.

**예외 상황**

- 인증 만료 시 로그인 화면으로 이동.

**관련 API**

- `GET /admin/orders`

---

## 2-4. 입금 확인

**설명**

관리자가 실제 계좌이체 내역을 확인한 뒤 해당 주문을 접수 처리한다.

**동작 흐름**

1. 관리자가 현장에서 이체 내역과 주문번호를 대조한다.
2. "입금 확인" 버튼으로 상태를 `PAYMENT_PENDING → ACCEPTED`로 변경한다.
3. 같은 트랜잭션에서 `payment_confirmed_at`을 서버 시각으로 기록하고 이력을 남긴다.

**주요 규칙**

- 일반 상태 변경 API로 `ACCEPTED`를 설정할 수 없다. 반드시 입금 확인 전용 API를 거친다.
- 고객의 요청만으로 자동 처리되지 않는다.

**예외 상황**

- 이미 다른 상태로 바뀐 경우 `ORDER_STATE_CONFLICT`.

**관련 API**

- `POST /admin/orders/:orderId/payment-confirmation`

## 2-5. 주문 상태 변경 (조리 시작 / 준비 완료 / 수령 완료)

**설명**

접수된 주문의 조리·수령 단계를 진행시킨다.

**동작 흐름**

1. 관리자가 현재 상태에 맞는 다음 단계 버튼을 누른다.
2. 허용된 전이만 반영하고 이력을 남긴다.

**주요 규칙**

- 허용 전이: `ACCEPTED → COOKING`, `COOKING → READY`, `READY → COMPLETED`
- 단계를 건너뛰는 전이(`ACCEPTED → READY` 등)나 역행(`READY → COOKING` 등)은 거절한다.
- 동시 요청(예: 입금확인과 취소가 동시에 옴)에서는 한쪽만 성공해야 한다(Row Lock 또는 조건부 UPDATE).

**예외 상황**

- 허용되지 않는 전이 요청 → `ORDER_STATE_CONFLICT`.

**관련 API**

- `PATCH /admin/orders/:orderId/status`

---

## 2-6. 주문 취소

**설명**

입금 전 주문을 취소한다.

**동작 흐름**

1. 관리자가 미입금 주문에 대해 취소를 누른다.
2. `PAYMENT_PENDING → CANCELLED`로 변경하고 이력을 남긴다.

**주요 규칙**

- 주문을 DELETE하지 않는다. 상태만 변경하고 이력을 보존한다.
- 입금 확인 이후에는 취소가 아니라 환불 기능을 사용한다.
- 미입금 주문의 자동 취소/자동 삭제는 없다(관리자가 수동으로만 처리).

**예외 상황**

- 이미 `ACCEPTED` 이후 상태면 취소 불가(`ORDER_STATE_CONFLICT`).

**관련 API**

- `POST /admin/orders/:orderId/cancel`

## 2-7. 환불

**설명**

입금 확인된 주문에 대해 전액 환불을 처리한다. 환불 여부 자체는 직원이 상황을 보고 판단하며, 시스템은 그 판단 결과를 기록·반영하는 역할만 한다.

**동작 흐름**

1. 고객이 환불을 요청하면(오프라인 상황 판단), 담당 직원이 환불 여부를 스스로 판단한다.
2. 환불하기로 했으면 관리자 화면에서 해당 주문에 환불 처리를 실행한다.
3. 원 주문 데이터(금액, 항목, 입금확인시각)는 변경하지 않고 별도 환불 기록을 추가한다.
4. 이력을 남긴다.

**주요 규칙 (확정)**

- 환불 가능 상태: `ACCEPTED`, `COOKING`, `READY`, `COMPLETED` — 이 범위 안이면 조리 진행 정도와 무관하게 아무 때나 환불할 수 있다.
- **전액 환불만 지원한다.** 부분 환불(일부 금액만 환불)은 지원하지 않는다. 환불 금액은 항상 해당 주문의 최종 결제 금액과 같다.
- **주문당 최대 1건만 환불할 수 있다**(전액 환불만 지원하므로 재환불이 필요 없다). 이미 환불된 주문에 다시 환불을 시도하면 거절한다.
- 환불해도 `OrderStatus`는 바뀌지 않는다. `REFUNDED`라는 새 상태를 추가하지 않는다. 조리·수령 흐름은 환불과 무관하게 그대로 진행된다(환불은 결제 기록에 대한 독립적인 정정일 뿐, 주문 자체를 취소하는 것이 아니다).
- 원 주문/항목/입금확인시각/총액을 수정하거나 0으로 만들지 않는다.
- 동일한 `refundRequestId` 재요청은 중복 환불 기록을 만들지 않는다(멱등성).
- 매출 통계에는 환불 처리일 기준으로 그 날짜의 환불액을 별도로 표시한다(원 결제액 자체는 건드리지 않는다). 자세한 내용은 `03_API명세서.md`의 `SalesView.refundedAmount` 참고.

**예외 상황**

- 환불 불가 상태(`PAYMENT_PENDING`, `CANCELLED`)에서 요청 시 오류.
- 이미 환불된 주문에 재요청 시 오류(`ORDER_STATE_CONFLICT`).

**관련 API**

- `POST /admin/orders/:orderId/refunds`

## 2-8. 주문 변경 이력 확인

**설명**

한 주문에 대해 생성부터 환불까지의 모든 처리 이력을 순서대로 확인한다.

**동작 흐름**

1. 관리자가 주문 상세에서 이력 조회를 요청한다.
2. 생성/입금확인/조리시작/준비완료/수령완료/취소/환불 이력을 시간순으로 반환한다.

**주요 규칙**

- append-only로만 기록한다. 기존 이력을 수정·삭제해 정정하지 않는다(필요하면 새 이력을 추가).
- 주문 상태 변경과 이력 기록은 같은 트랜잭션으로 처리되어, 한쪽만 저장되는 경우가 없다.

**예외 상황**

- 없음.

**관련 API**

- `GET /admin/orders/:orderId/history`

## 2-9. 메뉴 가격 변경 / 품절 상태 변경

**설명**

기존 메뉴의 가격이나 판매 가능 여부를 수정한다.

**동작 흐름**

1. 관리자가 메뉴 관리 화면에서 가격 또는 품절 여부를 변경한다.
2. 서버가 즉시 반영한다.

**주요 규칙**

- 수정 가능한 값은 가격(`price`)과 판매 여부(`isAvailable`)뿐이다.
- 메뉴 이름 변경, 메뉴 추가·삭제 기능은 없다.
- 자동 재고 차감 기능은 없다(관리자가 수동으로 품절 처리).
- 가격 변경은 이후의 새 주문에만 적용된다. 기존 주문의 스냅샷 가격은 유지된다.

**예외 상황**

- 존재하지 않는 메뉴ID 요청 시 오류.

**관련 API**

- `GET /admin/menus`
- `PATCH /admin/menus/:menuId`

## 2-10. 입금 계좌 관리

**설명**

고객에게 표시할 부스의 입금 계좌 정보를 관리한다.

**동작 흐름**

1. 관리자가 은행명/계좌번호/예금주를 조회·수정한다.
2. 저장 성공 시 이후 모든 고객 화면(과거 미입금 주문 포함)에 새 계좌가 표시된다.

**주요 규칙**

- 계좌번호는 숫자가 아니라 문자열로 저장한다(앞자리 0 보존).
- 서버 재시작 시 `.env` 기본값으로 DB의 현재 설정을 덮어쓰지 않는다.
- 일반 관리자 누구나 접근 가능하다(매출 비밀번호 재입력 불필요).

**예외 상황**

- 저장 실패 시 이전 값 유지, 오류 표시.

**관련 API**

- `GET /admin/settings/payment`
- `PATCH /admin/settings/payment`

## 2-11. 매출 조회

**설명**

입금 확인된 주문을 기준으로 판매 현황(오늘/축제 전체/일자별/메뉴별)을 확인한다.

**동작 흐름**

1. 관리자가 매출 화면에 진입할 때마다 현재 로그인한 계정의 비밀번호를 다시 입력한다.
2. 서버가 비밀번호를 검증하고 같은 응답으로 통계 전체를 반환한다.
3. 화면 이탈, 새로고침, 재진입 시 비밀번호를 다시 요구한다.

**주요 규칙**

- 매출 기준은 `payment_confirmed_at` + Asia/Seoul(KST)이다.
- `PAYMENT_PENDING`, 미입금 `CANCELLED`는 집계에서 제외한다.
- 별도의 매출 전용 JWT/Cookie/유지 세션은 없다. 요청마다 비밀번호를 재검증한다.
- 통계는 프론트엔드 메모리에만 두고 localStorage 등에 저장하지 않는다.
- **환불 반영(확정):** 원 결제 금액(`amount`)은 환불 여부와 무관하게 그대로 유지한다. 대신 환불이 처리된 날짜의 통계에 그날 발생한 환불액 합계(`refundedAmount`)를 별도로 보여준다. 순매출이 필요하면 화면에서 `amount - refundedAmount`로 계산해 표시한다.

**예외 상황**

- 비밀번호 불일치 → `SALES_PASSWORD_INVALID`.

**관련 API**

- `POST /admin/sales/query`

# 3. 시스템 기능

이 절은 고객·관리자 기능을 실제로 성립시키는 내부 메커니즘을 정리한다. 위에서 이미 설명한 기능은 중복 서술하지 않고 메커니즘 관점만 보충한다.

## 3-1. 주문 중복 방지 (멱등성)

**설명**

네트워크 재시도나 중복 클릭으로 동일한 주문이 두 번 생성되는 것을 막는다.

**동작 흐름**

1. 프론트엔드가 주문 시도마다 `orderRequestId`(UUID)를 생성해 전달한다.
2. 서버는 `orderRequestId`를 전역 UNIQUE로 관리한다(Guest 단위 스코프 없음).
3. 같은 ID + 같은 내용 → 기존 주문 반환. 같은 ID + 다른 내용 → 충돌 오류.

**주요 규칙**

- 가격은 멱등성 판단 기준(fingerprint)에 포함하지 않는다.
- 이미 COMMIT된 주문을 재시도 시점에 다시 생성하거나 롤백하지 않는다.

**예외 상황**

- 동시에 같은 ID로 여러 요청이 들어와도 주문은 하나만 생성된다.

**관련 API**

- `POST /orders`

---

## 3-2. 주문 상태 관리 및 동시성 제어

**설명**

주문 상태 전이를 정의된 규칙대로만 허용하고, 동시 요청 경합을 제어한다.

**주요 규칙**

- 상태 흐름: `PAYMENT_PENDING → ACCEPTED → COOKING → READY → COMPLETED`, 미입금 취소: `PAYMENT_PENDING → CANCELLED`
- 입금 확인과 취소처럼 상호 배타적인 요청이 동시에 오면 Row Lock(`FOR UPDATE`) 또는 조건부 UPDATE(영향받은 row 수 확인)로 한쪽만 성공시킨다.
- 상태 변경과 이력 기록은 하나의 DB Transaction으로 묶는다.

**관련 API**

- `POST /admin/orders/:orderId/payment-confirmation`, `PATCH /admin/orders/:orderId/status`, `POST /admin/orders/:orderId/cancel`

---

## 3-3. 메뉴 가격 Snapshot

**설명**

주문 시점의 메뉴 이름·가격을 별도로 저장해, 이후 메뉴 가격이 바뀌어도 과거 주문 금액이 변하지 않게 한다.

**주요 규칙**

- 주문 생성 트랜잭션 안에서 메뉴 현재 정보를 조회해 `order_items`에 그대로 복사(snapshot) 저장한다.
- 이후 `menus.price`가 바뀌어도 기존 `order_items`는 갱신하지 않는다.
- 과거 매출 계산도 이 snapshot 값을 사용하며 현재 `menus.price`로 재계산하지 않는다.

**관련 API**

- `POST /orders`, `POST /admin/sales/query`

---

## 3-4. 실시간 주문 생성/변경 알림

**설명**

주문 생성·상태 변경 사실을 관리자와 해당 고객에게 실시간에 가깝게 전달한다.

**동작 흐름**

1. 주문 관련 DB 변경이 COMMIT된 이후에만 이벤트(`order.created`, `order.updated`)를 발생시킨다.
2. Realtime 모듈이 이벤트를 구독해 Socket.IO로 전달한다.
3. 수신 측(관리자/고객)은 이벤트를 신호로만 사용하고, 실제 데이터는 REST로 다시 조회한다.

**주요 규칙**

- Socket.IO는 데이터 저장소가 아니다. PostgreSQL이 항상 최종 상태의 기준이다.
- 이벤트 발행은 DB COMMIT **이후**에만 한다(COMMIT 전 발행 금지).
- 같은 `orderRequestId` 재시도로 기존 주문을 반환하는 경우 `order.created`를 다시 발생시키지 않는다.
- 고객이 특정 주문 room에 참여하려면 이름+주문번호를 함께 제시해야 한다. `orderId`를 안다는 사실만으로는 구독을 허용하지 않는다.
- Socket 전송 실패가 주문 Transaction의 성공/실패에 영향을 주지 않는다.

**관련 API**

- Socket 이벤트 `order.created`, `order.updated` (`03_API명세서.md` 참고)

---

## 3-5. 관리자 인증 및 접근 제어

**설명**

관리자 전용 기능에 로그인한 관리자만 접근하도록 검증한다.

**주요 규칙**

- Backend 1(주문)과 Backend 2(운영) 모두 동일한 인증 검증(`AdminGuard`)을 공유해서 사용한다.
- 처리자 ID는 요청 body가 아니라 인증된 principal(JWT의 `sub`)에서만 가져온다.
- JWT 만료(30분) 시 REST 요청과 기존 Socket 접근을 모두 차단한다.

**관련 API**

- 모든 `/admin/*` API 공통
