# 축제 운영 검증 체크리스트

> v0.1 · 2026-09-20

이 문서는 **새 기능 명세도, 설계 변경도 아니다.** "개발상 정상 동작"과 "실제 축제 현장에서 장시간 운영해도 문제가 없는가"는 별개의 검증이라는 전제에서, 출시 전에 확인해야 할 항목만 체크리스트로 모은다.

여기서 다루는 정책·설계(관리자 JWT 12시간, Socket 재연결 후 REST 재조회, 단일 NestJS 프로세스, Nginx 라우팅 등)는 모두 `00_전체요약.md`, `001_백엔드_공통.md`, `002_백엔드1_주문결제.md`, `003_백엔드2_운영실시간.md`, `11_배포_체크리스트.md`, `frontend/000_프론트엔드_개발문서.md`에 이미 확정되어 있다. 이 문서는 그 결정을 재정의하지 않고, **실제로 지켜지는지 확인하는 항목만** 다룬다. 검증 중 기존 설계와 어긋나는 문제가 발견되면 이 문서를 고치지 말고 해당 설계 문서를 먼저 갱신한다.

# 1. 관리자 장시간 운영

시나리오: 관리자 페이지를 아이패드 등 한 기기에서 축제 운영시간 내내 켜 둔 채 사용한다.

- [ ] (실기기) 실제 운영시간(예: 하루 6~8시간) 동안 관리자 페이지를 켜 둔 상태로 연속 사용 테스트를 진행한다.
- [ ] (구현됨) 관리자 JWT 12시간 만료 정책(`001` §41, `003` §7)을 확인하고, 하루 운영시간이 12시간을 넘는 날이 있는지 먼저 확인한다. 넘는 날이 있으면 그날은 중간 재로그인이 필요하다는 것을 운영자에게 미리 안내한다(정책 자체를 바꾸지 않는다).
- [ ] (구현됨) 정상적인 사용 흐름에서 12시간 이내에 불필요한 재로그인이 발생하지 않는지 확인한다(Refresh Token 없음이 확정 정책 — `001` §41).
- [ ] (구현됨) 정상 로그아웃 시 그 로그인 세션(기기)의 Socket 연결이 즉시 종료되는지 브라우저 개발자도구(Network → WS)로 확인한다(`003` §10, `realtime.gateway.ts` `disconnectAdmin`).
- [ ] (구현됨) JWT 실제 만료 시각에 도달하면 REST 요청(`ADMIN_UNAUTHORIZED`)과 기존 Socket 연결이 모두 종료되는지 확인한다(`001` §41). 12시간을 그대로 기다리기 어려우면 테스트 환경에서만 짧은 만료 시간으로 임시 검증하고, 실제 12시간 만료 시나리오도 별도로 최소 1회 확인한다.

# 2. 관리자 기기

- [ ] (실기기) 실제 아이패드/태블릿 기종으로 테스트한다(데스크톱 브라우저 화면 축소로 대체하지 않는다).
- [ ] (실기기) 기기의 자동 화면 잠금 시간을 축제 운영시간보다 길게 설정하거나 "항상 켜짐"으로 바꿨는지 확인한다.
- [ ] (실기기) 충전 케이블을 상시 연결해 배터리 부족으로 인한 강제 종료 가능성을 없앤다.
- [ ] (실기기) 브라우저를 수 시간 동안 열어 둔 상태에서 OS/브라우저의 백그라운드 자원 회수로 인한 임의 새로고침·탭 재시작이 없는지 확인한다.
- [ ] (Step 7) 화면 잠금 해제 후(백그라운드 복귀) 주문 목록·상태가 최신인지 확인한다. Socket 재연결과 REST 재조회가 함께 동작해야 한다(`003` §32).

# 3. 네트워크 및 Socket 복구

- [ ] (실기기) Wi-Fi를 일시적으로 끄고 다시 켰을 때 Socket.IO가 재연결되는지 확인한다.
- [ ] (실기기) Wi-Fi ↔ LTE/5G 등 네트워크 인터페이스가 바뀌는 상황에서도 재연결되는지 확인한다.
- [ ] (Step 7) 재연결 시 재인증(관리자는 JWT Cookie, 고객은 이름+주문번호)과 room 재검증이 이루어지는지 확인한다(`003` §32, `001` §37).
- [ ] (Step 7~8) 재연결 후 REST로 최신 주문 상태를 다시 조회하는지 확인한다(`003` §32 "이벤트 누락이나 순서 역전은 REST 재조회로 복구").
- [ ] (Step 7~8) 연결이 끊긴 동안 발생한 주문 생성/상태 변경이 재연결 후 REST 재조회로 모두 반영되는지 확인한다. Socket 이벤트 자체는 영속 저장이나 재전송을 보장하지 않는다는 것이 이미 확정된 설계다(`001` §37 "Event 전달 보장").
- [ ] 이 섹션에서 확인하는 것은 "Socket = 변경 알림, PostgreSQL/REST = 최종 상태"라는 기존 설계(`00_전체요약.md` "도메인 간 연결")가 실제로 지켜지는지이며, 이 설계 자체를 새로 만들거나 바꾸지 않는다.

# 4. 다중 관리자

- [ ] (실기기, Step 6 이상) 서로 다른 관리자 계정으로 기기 2대 이상에서 동시 로그인한다.
- [ ] 한 관리자가 만든 신규 주문이 다른 관리자 화면에도 실시간으로 반영되는지 확인한다. **주의:** 현재 코드는 `order.created` → 관리자 전체 broadcast(admin room)까지만 구현되어 있고(구현됨), 상태 변경 알림인 `order.updated`의 관리자 전달은 아직 구현되지 않았다(`003` §39 Step 7 예정). Step 7 완료 후 "다른 관리자가 입금확인·조리중 등으로 바꾼 상태가 내 화면에도 반영되는지"를 반드시 재확인한다.
- [ ] (Step 2 완료 후, `002` §19) 같은 주문을 두 관리자가 거의 동시에 조작(예: 한 명은 입금 확인, 한 명은 취소)했을 때 Row Lock 또는 조건부 `UPDATE`로 하나만 성공하는지 확인한다(`001` §57 공통 테스트 표 "입금 vs 취소: 하나만 성공"). 새로운 동시성 로직을 만들지 않고, 이미 정의된 정책이 실제로 지켜지는지만 확인한다.
- [ ] (구현됨) 한 관리자가 로그아웃해도 다른 관리자의 Socket 연결에는 영향이 없는지 확인한다(`disconnectAdmin`은 로그아웃한 세션의 `adminId`와 `jti` 세션 식별자가 모두 일치하는 소켓만 종료한다).
- [ ] (구현됨) 같은 관리자 계정으로 기기 2대(예: 아이패드 2대)에서 각각 로그인한 뒤 한쪽에서만 로그아웃하면, 그 기기의 Socket만 끊기고 다른 기기는 로그인 상태와 Socket 연결이 그대로 유지되는지 확인한다(`jti` 세션 식별자 매칭, `003` §10 확정 2026-09-20).

# 5. 주문 실운영

QR 접속 → 메뉴 선택 → 주문 생성 → 주문번호 발급 → 계좌 확인 → 실제 운영 방식에 따른 입금 확인 → 관리자 결제 확인 → 조리중 → 준비완료 → 고객 상태 확인 → 완료, 전체 흐름을 실제 고객 휴대폰과 관리자 기기로 검증한다.

- [ ] (구현됨) QR 접속 → 메뉴 선택 → 이름+전화번호 입력 → 주문 생성(`POST /orders`) → 주문번호 발급
- [ ] (구현됨) 계좌 확인(`GET /settings/payment`)
- [ ] (미구현 — Backend 1 주문 API 완성 후) 실제 운영 방식에 따른 입금 확인 절차 리허설(현장 이체 내역과 주문번호 대조)
- [ ] (미구현 — Step 6/7) 관리자 결제 확인(`POST /admin/orders/:orderId/payment-confirmation`) → 조리중(`PATCH .../status` COOKING) → 준비완료(READY)
- [ ] (미구현 — Step 7) 고객 화면에서 상태 변경이 실시간으로 반영되는지(`order.updated` → 고객 room)
- [ ] (미구현 — Step 8) 수령완료(COMPLETED) 처리

추가로 확인할 시나리오(모두 위 API 구현 완료 후):

- [ ] 여러 주문이 짧은 시간에 연속으로 생성되는 상황에서 각 주문 Transaction의 정합성(`002` §14)
- [ ] 동일 메뉴에 주문이 몰리는 상황 — 자동 재고 관리는 정책상 사용하지 않으므로(`00_전체요약.md` "현재 제외") 품절 처리로만 대응되는지 확인
- [ ] 관리자가 메뉴를 품절 처리한 뒤, 이미 열려 있던 고객 화면에서 해당 메뉴로 주문을 시도하면 서버가 최종 검증으로 거절하는지(`003` §15 "고객 화면 메뉴 정보가 오래된 상태라도 주문 최종 검증은 Backend에서 다시 수행")
- [ ] 주문 취소(`POST /admin/orders/:orderId/cancel`, `PAYMENT_PENDING → CANCELLED`만 가능)
- [ ] 환불 처리(`POST /admin/orders/:orderId/refunds`, 전액·주문당 1건, `OrderStatus` 불변 — `002` §24)
- [ ] 고객이 페이지를 닫았다가 이름+주문번호로 재조회(`POST /orders/lookup`, localStorage 자동 복구 포함 — `frontend/000` §6~7)
- [ ] 고객 기기의 네트워크가 끊겼다가 복구될 때 Socket 재연결 + REST 재조회로 최신 상태가 보이는지(`003` §32)

# 6. 서버 장애/재시작

- [ ] (배포) NestJS 프로세스를 실제로 재시작했을 때의 동작을 확인한다.
- [ ] (배포) 재시작 후 기존에 연결돼 있던 관리자/고객 Socket이 Socket.IO 표준 재연결 로직으로 다시 붙는지 확인한다.
- [ ] (배포) 재연결 후 REST로 최신 상태를 다시 가져오는지 확인한다. 재시작 중에는 in-process 이벤트 자체가 소실되므로 재전송을 보장하지 않는다는 것이 이미 확정된 설계다(`001` §37).
- [ ] (배포) 재시작 전후로 PostgreSQL 데이터(주문·이력·메뉴·계좌 설정)가 그대로 유지되는지 확인한다. 재시작 스크립트가 의도치 않게 마이그레이션/시드를 재실행하지 않는지도 함께 확인한다.
- [ ] (배포) 서버 재시작 동안(수 초~수십 초) 고객·관리자 화면이 어떻게 보이는지 확인한다. 연결 끊김 표시가 있는지, 무한 로딩으로만 보이지 않는지 체감 기준으로 점검한다. 정확한 재시도 주기는 프론트 문서에서도 아직 미정(`frontend/000` §6 "정확한 재시도·재조회 주기는 미정")이므로, 이 문서에서 새로 확정하지 않고 발견한 문제만 기록한다.

# 7. 배포 환경

MVP는 in-process EventEmitter + Socket.IO 구조이므로 Redis Adapter / Kafka / RabbitMQ 등은 이번 범위에서 도입하지 않는다(`001` §37, `003` §37 — 기존 확정 설계 그대로).

- [ ] (배포) 단일 NestJS 프로세스로 운영되는지 확인한다. **이유:** `order.created`/`order.updated`는 프로세스 내부(in-process) `EventEmitter`로 전달되고, 기본 Socket.IO adapter도 프로세스 간 room을 공유하지 않는다(`003` §37 확정). PM2 등을 사용하더라도 **cluster 모드(다중 인스턴스)는 사용하지 않고 fork 모드 1개 인스턴스로 제한**한다. 여러 프로세스를 띄우면 한 프로세스가 처리한 주문 이벤트가 다른 프로세스에 연결된 관리자/고객 Socket에는 전달되지 않는 문제가 생긴다.
- [ ] (배포) 단일 인스턴스가 비정상 종료됐을 때 자동 재기동되는 워치독(PM2 fork 모드 등)이 있는지 확인한다 — 여러 인스턴스를 동시에 띄우는 것과는 별개로, 단일 인스턴스의 비정상 종료 후 자동 재시작 자체는 필요하다.
- [ ] (배포) Nginx `/socket.io/*` 라우팅에 WebSocket Upgrade 설정이 되어 있는지 확인한다. 기존 `11_배포_체크리스트.md`에 이 항목을 동기화했다(아래 "관련 문서" 참고).
- [ ] (배포) `11_배포_체크리스트.md`의 기존 항목(§0~5: PaymentSettings seed, Reverse Proxy/IP 식별, Rate Limit, 환경변수, 메뉴 사진/CDN)이 모두 완료됐는지 확인한다.

# 8. 주문 폭주/운영성

- [ ] (Step 7 이후, 실운영) 주문이 연속으로 들어와도 관리자 화면(`GET /admin/orders` 커서 페이지네이션 + `order.created` 알림)에서 신규 주문이 누락 없이 보이는지 확인한다.
- [ ] (Step 7 이후, 실운영) **피크타임 관리자 주문 처리성 검증**: 주문이 짧은 시간에 다수 누적된 상황을 시뮬레이션해, 현재 관리자 주문 목록 API(`GET /admin/orders` 커서 페이지네이션)와 프론트 화면만으로 실제 운영이 가능한지 확인한다(새 API나 새 UI 방식을 이 항목에서 확정하지 않는다).
  - [ ] 주문이 많이 쌓인 상태에서도 지금 처리해야 할 주문을 화면에서 빠르게 찾을 수 있는지
  - [ ] `PAYMENT_PENDING` / `ACCEPTED` / `COOKING` / `READY` 등 상태별 주문 건수를 쉽게 파악할 수 있는지
  - [ ] 오래 대기 중인 주문을 식별할 수 있는지
  - [ ] 상태별 탭 / 필터 / 보드 등 현재 화면 구성 방식이 실제 아이패드 운영에 적합한지
  - [ ] 한 주문의 상태가 변경됐을 때 그 주문이 변경된 상태에 맞는 화면 영역에 자연스럽게 반영되는지
  - [ ] 여러 관리자가 동시에 사용할 때 다른 관리자가 변경한 주문 상태도 내 화면에 정상 반영되는지(`order.updated` 관리자 전달, `003` §39 Step 7 — 4. 다중 관리자 섹션과 함께 확인)

  검증 결과 UI 표현(구분·강조·정렬 등)만 부족하면 프론트 화면 개선을 검토하고, 현재 관리자 주문 목록 API 자체로는 위 항목을 만족할 수 없다고 판단되면 그때 Backend 1의 관리자 주문 목록 API에 상태별 조회/필터 확장이 필요한지 별도로 검토한다.
- [ ] (Step 7 이후) 같은 버튼을 중복 클릭했을 때 중복 요청/중복 상태 전이가 발생하지 않는지 확인한다 — 프론트의 "처리 중 버튼 잠금"(`frontend/000` §4 구현 초안)과 백엔드의 조건부 `UPDATE`(`002` §19)가 함께 지켜지는지 본다.
- [ ] (Step 7 이후) 여러 관리자가 동시에 같은 주문을 조작해도 하나만 성공하는지, 폭주 상황에서도 재확인한다(4. 다중 관리자 섹션과 동일 정책, 부하가 걸린 상태에서의 재검증).
- [ ] API 오류(4xx/5xx) 발생 시 화면에 오류가 표시되고 운영자가 상황을 인지할 수 있는지 확인한다. 성공으로 잘못 표시되는 사례(silent failure)가 없는지 점검한다(`frontend/000` §10 완료 확인 항목 "상태 충돌·요청 실패 시 재조회되며 성공으로 잘못 표시되지 않는다").

# 9. 축제 시작 전 최종 Smoke Test

- [ ] (배포+실기기) 실제 배포된 production 환경(Oracle HTTPS)에서 고객 실제 휴대폰 1대 + 관리자 실제 아이패드 1대로 최소 1회, 전체 주문 lifecycle(QR → 주문 → 입금 확인 → 조리중 → 준비완료 → 수령완료)을 통과시킨다.
- [ ] (배포+실기기) 가능하면 고객 기기 2대 이상 + 관리자 기기 2대 이상으로 확장해 테스트한다.
- [ ] 이 스모크 테스트는 `003_백엔드2_운영실시간.md` §39 Step 12(실제 기기 테스트) 실행 시점에 이 문서 전체와 함께 진행한다 — Step 12 자체 항목은 `003`에 이미 있으므로 여기서 중복 작성하지 않는다.

# 10. 이 문서에서 다루지 않는 것

- Redis Adapter, Kafka, RabbitMQ 등 메시지 브로커 도입 — 현재 MVP 범위 밖(`001` §37, `003` §37).
- Refresh Token, 매출 전용 JWT — 현재 확정 정책에서 제외(`00_전체요약.md` "현재 제외").
- 새로운 API, 새로운 DB 컬럼, 새로운 화면 — 이 문서는 검증 항목만 정의하며 구현 범위를 넓히지 않는다.
