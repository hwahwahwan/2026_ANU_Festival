# Backend 1 — 주문·결제 도메인

> v0.10 · 2026-09-18

Backend 1은 고객 식별부터 주문 완료·취소·환불까지 **주문의 전체 생명주기**를 담당한다.

공통 구현 규칙은 `001_백엔드_공통.md`를 따른다.

---

# 1. 담당 범위

```text
Order
OrderItem
OrderHistory

OrderDailyCounter

고객 식별 (이름 + 전화번호, 주문에 직접 저장)
```

> v0.9부터 별도의 Guest 등록/쿠키 식별을 사용하지 않는다. 고객 식별은 "주문 생성 시 입력한 이름 + 전화번호"와 "이름 + 주문번호 조회"만으로 처리한다. 이유와 비교는 `# 6. 고객 정보 입력`을 참고한다.

향후 TossPayments 테스트 결제를 추가할 경우 Payment 도메인도 Backend 1이 담당한다.

현재 MVP에는 온라인 PG를 구현하지 않는다.

# 6. 고객 정보 입력

## Guest 쿠키를 사용하지 않는다

별도의 "손님 등록" 단계(Guest 생성, Cookie 발급)를 두지 않는다.

고객은 주문할 때 **이름 + 전화번호**를 주문 요청에 직접 담아 보낸다.

```text
메뉴 담기
   ↓
이름 + 전화번호 입력
   ↓
POST /orders
   ↓
orders.customer_name / orders.customer_phone 저장
```

전화번호는 주문을 찾아가지 않을 때 연락하기 위한 **연락처**일 뿐이며, 이름·전화번호 어느 쪽도 로그인/세션 식별에 사용하지 않는다.

---

## 왜 쿠키를 쓰지 않는가

- 주문 생성 시점에는 아직 주문번호가 없으므로, 그 시점에 "누구인지" 확인할 다른 수단(쿠키 등)이 필요 없다 — 이름/전화번호를 그 자리에서 그대로 받아서 저장하면 된다.
- 이후 "내 주문 확인"은 `POST /orders/lookup`(이름 + 주문번호) 하나로 통일한다. 새로고침 시 재입력이 필요 없도록 하는 것은 서버 세션이 아니라 **프론트엔드 localStorage**(주문 직후 이름+주문번호를 저장)가 담당한다.
- 서버가 어떤 형태로든 "이 브라우저가 누구인지" 기억하는 상태(Cookie, Session)를 갖지 않으므로 Guest 테이블 자체가 필요 없다.

---

## 동명이인

이름은 UNIQUE가 아니다.

```text
홍길동 → 주문 0917-0001
홍길동 → 주문 0917-0002
```

가능하다. 서로 다른 주문으로 각각 존재하며, 서버가 이름만으로 두 주문을 같은 사람 것으로 합치지 않는다. 조회는 항상 "이름 + 주문번호" 쌍으로만 이루어지므로 동명이인이어도 서로 다른 주문이 섞이지 않는다.

# 7~8. 주문 조회 — 이름 + 주문번호

고객이 자신의 주문을 확인하는 방법은 다음 하나뿐이다.

```http
POST /orders/lookup
```

입력:

```text
이름 + 주문번호
```

로 주문 **한 건**을 찾는다. (`GET /orders/me`, `GET /orders/:orderId` 같은 세션 기반 "내 주문 목록" API는 두지 않는다 — 서버가 유지하는 로그인 세션이 없기 때문이다.)

성공해도:

```text
과거 주문 전체 복구 X (이름만으로 그 사람의 모든 주문을 보여주지 않는다)
```

해당 주문 한 건만 반환한다.

두 번 이상 주문한 고객은 프론트엔드가 localStorage에 `[{name, orderNumber}, ...]` 형태로 여러 건을 저장해두고, 화면에서 각각 `POST /orders/lookup`을 호출해 개별 조회한다. "여러 주문을 한 번에 묶어서 보여주는" 서버 API는 없다.

새로고침 시 재입력이 필요 없는 것은 프론트엔드가 localStorage 값으로 자동으로 lookup을 다시 호출하기 때문이며, 서버 상태와는 무관하다.

다른 기기/브라우저로 접속했거나 localStorage가 지워졌을 때만 이름+주문번호를 직접 다시 입력한다.

# 9. 주문 생성 입력

예:

```json
{
  "orderRequestId": "uuid",
  "customerName": "홍길동",
  "customerPhone": "010-1234-5678",
  "items": [
    {
      "menuId": "uuid",
      "quantity": 2
    }
  ]
}
```

`customerName`/`customerPhone`은 Guest 쿠키가 없으므로 이 요청에서 직접 받는 값이 원본이다. DTO 레벨 형식 검증(길이, 전화번호 형식)은 거치지만, "다른 어딘가에 저장된 진짜 값"이 따로 있는 게 아니라 이 입력값 자체가 `orders.customer_name` / `orders.customer_phone`으로 그대로 저장된다.

클라이언트가 다음 값은 보내더라도 신뢰하지 않는다.

```text
menu price
totalPrice
```

가격은 서버가 DB에서 조회한다.

# 11. 주문번호

표시 형식:



---

## 번호 발급

`COUNT(*) + 1`을 사용하지 않는다.

`order_daily_counters`를 원자적으로 갱신한다.

예시:

```sql
INSERT INTO order_daily_counters (
  order_date,
  last_number
)
VALUES ($1::date, 1)

ON CONFLICT (order_date)
DO UPDATE
SET last_number =
  order_daily_counters.last_number + 1

RETURNING last_number;
```

이 쿼리는 주문 생성 Transaction 안에서 실행한다.

번호가 빈틈없이 연속일 필요는 없다.

중복되지 않는 것이 중요하다.

---

## 9999 초과 처리 (확정)

`last_number`에 `CHECK (last_number BETWEEN 1 AND 9999)` 제약을 둔다.

하루 9999건을 넘는 주문 시도는 이 CHECK 위반으로 실패하며, 서비스 레이어가 이를 `DAILY_ORDER_LIMIT_EXCEEDED`(409) 오류로 변환해 응답한다. 다음 구간(예: 알파벳 접미사)으로 자동 확장하지 않는다. 실사용상 하루 9999건을 넘길 가능성은 거의 없다고 보고 이 이상은 대응하지 않는다.

# 12. 멱등성

프론트는 주문 시도 하나마다 UUID를 생성한다.

```text
orderRequestId
```

네트워크 재시도에서는 같은 ID를 사용한다.

DB 후보:

```text
UNIQUE(order_request_id)
```

Guest 개념이 없으므로 `order_request_id` 자체를 전역으로 UNIQUE 처리한다(별도 guest 스코프 불필요).

---

## 같은 요청

```text
같은 orderRequestId
같은 주문 내용
```

이면 기존 주문을 반환한다.

새 주문번호를 발급하지 않는다.

---

## 다른 요청

같은 requestId인데 주문 내용이 다르면:

```text
IDEMPOTENCY_CONFLICT
```

를 반환한다.

# 13. Request Fingerprint

동일 requestId에 다른 주문 내용이 들어오는 것을 검사하기 위해 fingerprint를 사용할 수 있다.

가격은 fingerprint에 포함하지 않는다.

예:

```text
menuId + quantity
```

를 정렬된 형태로 정규화한 뒤 hash한다.

배열 순서만 다른 요청이 다른 주문으로 인식되지 않도록 한다.

중복 menuId를 합산할지 오류 처리할지는 구현 전에 확정한다.

# 19. 동시성 처리


## 구현 방법

다음 중 하나를 사용한다.

### Row Lock

```sql
SELECT *
FROM orders
WHERE id = $1
FOR UPDATE;
```

이후 현재 상태를 확인한다.

또는 조건부 UPDATE를 사용한다.

```sql
UPDATE orders
SET status = 'ACCEPTED'
WHERE id = $1
  AND status = 'PAYMENT_PENDING';
```

영향받은 row 수를 확인한다.

# 24. Refund

**환불 정책 (2026-09-18 확정)**

환불 가능 상태(상태와 무관하게, 조리 진행 정도와 상관없이 직원 판단으로 아무 때나 가능):

```text
ACCEPTED
COOKING
READY
COMPLETED
```

**전액 환불만 지원한다. 부분 환불은 없다.** 환불 여부 자체는 시스템이 판단하지 않고 직원이 상황을 보고 결정하며, 시스템은 그 결정을 기록·반영하는 역할만 한다.

원 주문 데이터는 유지한다.

```text
orders
order_items
payment_confirmed_at
total_price
```

를 변경하거나 0으로 만들지 않는다. 환불해도 `OrderStatus`는 바뀌지 않는다(`REFUNDED` 상태를 추가하지 않는다). 조리/수령 흐름도 환불과 무관하게 그대로 진행된다.

**주문당 최대 1건만 환불 가능하다**(전액 환불만 지원하므로 재환불이 필요 없다).

---

## 환불 기록 (확정)

```text
id
order_id            -- UNIQUE (주문당 최대 1건)
refund_request_id   -- UNIQUE (멱등성 키)
amount              -- 항상 orders.total_price와 동일 (전액 환불만 지원)
processed_at
processed_by
reason              -- 선택
```

환불 역시 History를 추가한다(`actor_type = 'ADMIN'`).

---

## 환불 멱등성 (확정)

```text
UNIQUE(order_id)
UNIQUE(refund_request_id)
```

동일 `refundRequestId` 요청이 반복되면 새 환불을 만들지 않고 기존 결과를 반환한다. 이미 환불된 주문(`order_id` UNIQUE 위반)에 다른 `refundRequestId`로 재요청하면 `ORDER_STATE_CONFLICT`로 거절한다.

---

## 매출 반영 (확정)

환불 처리일(`processed_at`)을 기준으로 그 날짜의 매출 통계에 환불액을 별도로 표시한다(원 결제 `total_price`/`amount` 자체는 건드리지 않는다). 상세 응답 구조는 `001_백엔드_공통.md` §44 `SalesView.refundedAmount` 참고.

## 성능/인덱스 후속 검토 (Backend 2 Sales 관련, 지금은 필요 없음)

Sales(Backend 2)의 모든 매출 집계 쿼리는 `orders.payment_confirmed_at` 범위 조건으로 `orders`를 필터링한 뒤 `order_items`와 JOIN한다(`003_백엔드2_운영실시간.md` §22 참고). 이 테이블은 Backend 1이 소유하므로 Backend 2가 임의로 인덱스 Migration을 추가하지 않는다(§27 침범 금지). 학교 축제 규모(소량 주문)에서는 순차 스캔으로도 충분할 가능성이 높아 지금 단계에서 인덱스를 추가하지 않는다. 실제 배포 후 주문량과 쿼리 플랜(`EXPLAIN ANALYZE`)을 확인한 뒤 필요하면 Backend 1이 `orders.payment_confirmed_at`에 인덱스를 추가하는 Migration(`b1_XXX_*.sql`)을 만드는 것을 후속 작업으로 남긴다.

# 25. Realtime Event

Backend 1은 Socket.IO Gateway를 구현하지 않는다.

DB 변경 COMMIT 후 event만 발행한다.

---

## 신규 주문

```text
COMMIT
  ↓
order.created
```

payload:

```ts
{
  orderId: string;
}
```

---

## 주문 변경

```text
COMMIT
  ↓
order.updated
```

payload:

```ts
{
  orderId: string;
  status: OrderStatus;
}
```

Socket 전송 실패가 주문 Transaction 실패를 의미하지 않는다.

이미 COMMIT된 주문을 다시 생성하거나 Rollback하려고 하지 않는다.

# 30. 완료 기준

Backend 1 완료 조건:

- 이름 + 주문번호로 주문을 조회할 수 있다 (Guest 쿠키 없이).
- 이름만 맞고 주문번호가 틀리면(또는 그 반대) 조회되지 않는다.
- lookup이 주문 1건만 반환한다.
- 서버 가격으로 주문이 생성된다.
- 과거 주문 가격 snapshot이 보존된다.
- 주문번호가 동시 요청에도 중복되지 않는다.
- 동일 orderRequestId가 주문 하나만 만든다.
- 주문/항목/History가 원자적으로 저장된다.
- 잘못된 상태 전이가 차단된다.
- 입금 확인과 취소 경합이 제어된다.
- 모든 처리 이력이 보존된다.
- 이벤트는 COMMIT 후에만 발생한다.
- 중복 환불이 방지된다(`refundRequestId` 멱등성).
- 실제 PostgreSQL에서 동시성 테스트를 통과한다.
