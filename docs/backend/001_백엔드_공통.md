# 백엔드 공통 — 구현 계약·기술 규칙

> v0.11 · 2026-09-18

이 문서는 Backend 1과 Backend 2가 개발 전에 반드시 동일하게 사용해야 하는 **공통 구현 계약**을 정의한다.

도메인 내부 업무 로직은 각각 다음 문서에서 관리한다.

```text
002_백엔드1_주문결제.md
003_백엔드2_운영실시간.md
```

전체 서비스 흐름과 개발 순서는 다음 문서를 따른다.

```text
00_전체요약.md
01_백엔드_개발문서.md
```

이 문서에 정의된 공통 계약은 Backend 1/2가 각각 따로 구현하지 않는다.

하나의 구현을 공유한다.

# 8. 공통 계약 1 — DatabaseModule

DatabaseModule은 Backend 1/2가 공유하는 PostgreSQL 연결을 관리한다.

프로젝트 전체에서 **Pool은 하나만 생성한다.**

각 도메인에서 개별적으로 `new Pool()`을 만들지 않는다.

---

## DatabaseModule 책임

```text
PostgreSQL Pool 생성

DB 연결 관리

일반 Query

Transaction

애플리케이션 종료 시 Pool 종료
```

---

## DatabaseService

공통으로 다음 인터페이스를 사용한다.

```ts
import {
  Pool,
  PoolClient,
  QueryResult,
  QueryResultRow,
} from 'pg';

export class DatabaseService {
  private readonly pool: Pool;

  async query<T extends QueryResultRow>(
    text: string,
    params: readonly unknown[] = [],
  ): Promise<QueryResult<T>>;

  async withTransaction<T>(
    work: (client: PoolClient) => Promise<T>,
  ): Promise<T>;

  async onApplicationShutdown(): Promise<void>;
}
```

---

## 일반 Query

Transaction이 필요하지 않은 단일 Query:

```ts
const result = await database.query(
  'SELECT * FROM menus WHERE id = $1',
  [menuId],
);
```

---

## Transaction

공통 Transaction 구현:

```ts
async withTransaction<T>(
  work: (client: PoolClient) => Promise<T>,
): Promise<T> {
  const client = await this.pool.connect();

  try {
    await client.query('BEGIN');

    const result = await work(client);

    await client.query('COMMIT');

    return result;
  } catch (error) {
    try {
      await client.query('ROLLBACK');
    } catch {
      // rollback 오류는 별도 내부 로그 처리
    }

    throw error;
  } finally {
    client.release();
  }
}
```

---

## 사용 예

```ts
return this.database.withTransaction(async (client) => {
  const menus =
    await this.menuReader.getSnapshotsForOrder(
      client,
      menuIds,
    );

  const order =
    await this.ordersRepository.create(
      client,
      orderData,
    );

  await this.orderItemsRepository.createMany(
    client,
    order.id,
    items,
  );

  return order;
});
```

---

## Transaction 규칙

Transaction 안에서 사용하는 모든 Query는 **같은 `PoolClient`**를 사용한다.

```text
BEGIN

Menu 조회
Order 생성
OrderItem 생성
History 생성

COMMIT
```

모두 같은 client다.

다음은 금지한다.

```ts
database.withTransaction(async (client) => {
  await client.query(...);

  // 금지
  await database.query(...);
});
```

Transaction 중 별도 Pool connection으로 빠져나가면 안 된다.

---

## Repository 규칙

Transaction이 필요한 Repository 함수는 `PoolClient`를 인자로 받는다.

예:

```ts
async create(
  client: PoolClient,
  data: CreateOrderData,
): Promise<OrderRow>
```

```ts
async appendHistory(
  client: PoolClient,
  history: OrderHistoryData,
): Promise<void>
```

# 9. SQL 공통 규칙

모든 값은 parameter binding을 사용한다.

사용:

```sql
SELECT *
FROM menus
WHERE id = $1;
```

금지:

```ts
`SELECT *
 FROM menus
 WHERE id = '${menuId}'`
```

---

## 동적 SQL

정렬 컬럼처럼 parameter binding을 사용할 수 없는 항목은 허용 목록을 사용한다.

예:

```ts
const allowedSort = {
  createdAt: 'created_at',
  orderNumber: 'order_number',
};
```

사용자 입력을 그대로 SQL 식별자로 사용하지 않는다.

# 13. 공통 계약 2 — OrderStatus

`OrderStatus`는 한 곳에서만 정의한다.

파일:

```text
src/common/contracts/order-status.ts
```

```ts
export const ORDER_STATUS = {
  PAYMENT_PENDING: 'PAYMENT_PENDING',
  ACCEPTED: 'ACCEPTED',
  COOKING: 'COOKING',
  READY: 'READY',
  COMPLETED: 'COMPLETED',
  CANCELLED: 'CANCELLED',
} as const;

export type OrderStatus =
  typeof ORDER_STATUS[keyof typeof ORDER_STATUS];
```

각 도메인에서 별도의 OrderStatus enum/type을 만들지 않는다.

---

## 상태 흐름

```text
PAYMENT_PENDING
      ↓
ACCEPTED
      ↓
COOKING
      ↓
READY
      ↓
COMPLETED
```

취소:

```text
PAYMENT_PENDING → CANCELLED
```

환불은 현재 OrderStatus에 임의로 `REFUNDED`를 추가하지 않는다.

환불 상태 모델은 환불 정책 확정 후 함께 변경한다.

# 15. Request DTO 규칙

실제 HTTP Request Validation용 DTO는 각 도메인에서 class로 만든다.

예:

```ts

  orderRequestId: string;

  @ValidateNested({ each: true })

```

공통 문서의 interface/type은 **도메인 간 계약**을 위한 것이며 runtime validation을 대신하지 않는다.

# 17. 공통 API 성공 응답 규칙

Controller는 실제 응답 객체를 그대로 반환한다.

예:

```json
{
  "id": "...",
  "name": "크로플",
  "price": 3500,
  "isAvailable": true
}
```

목록:

```json
[
  {
    "id": "...",
    "name": "크로플",
    "price": 3500,
    "isAvailable": true
  }
]
```

로그인 / 로그아웃처럼 body가 필요 없는 요청은 `204 No Content`를 사용할 수 있다.

# 18. 공통 오류 계약

모든 API 오류는 다음 구조로 통일한다.

```ts
export interface ApiErrorBody {
  code: string;
  message: string;
}
```

예:

```json
{
  "code": "ORDER_STATE_CONFLICT",
  "message": "현재 주문 상태에서는 처리할 수 없습니다."
}
```

---

## 공통 Error Code

```ts
export const ERROR_CODE = {
  VALIDATION_ERROR: 'VALIDATION_ERROR',

  MENU_UNAVAILABLE: 'MENU_UNAVAILABLE',

  IDEMPOTENCY_CONFLICT: 'IDEMPOTENCY_CONFLICT',

  ORDER_NOT_FOUND: 'ORDER_NOT_FOUND',

  ORDER_STATE_CONFLICT: 'ORDER_STATE_CONFLICT',

  ADMIN_UNAUTHORIZED: 'ADMIN_UNAUTHORIZED',

  ADMIN_LOGIN_FAILED: 'ADMIN_LOGIN_FAILED',

  DAILY_ORDER_LIMIT_EXCEEDED: 'DAILY_ORDER_LIMIT_EXCEEDED',

  SALES_PASSWORD_INVALID:
    'SALES_PASSWORD_INVALID',

  UNAUTHORIZED: 'UNAUTHORIZED',

  FORBIDDEN: 'FORBIDDEN',

  NOT_FOUND: 'NOT_FOUND',

  CONFLICT: 'CONFLICT',

  TOO_MANY_REQUESTS: 'TOO_MANY_REQUESTS',

  INTERNAL_ERROR: 'INTERNAL_ERROR',
} as const;
```

`UNAUTHORIZED` / `FORBIDDEN` / `NOT_FOUND` / `CONFLICT` / `TOO_MANY_REQUESTS` / `INTERNAL_ERROR`는 명시적인 도메인 code 없이 HTTP status만으로 끝나는 오류를 위한 공통 fallback code다.

`ApiException`으로 명시적인 domain error code(`ORDER_NOT_FOUND`, `ADMIN_UNAUTHORIZED` 등)를 던진 경우 그 code를 그대로 유지하며, 이 fallback code로 대체하지 않는다.

`ADMIN_LOGIN_FAILED`와 `ADMIN_UNAUTHORIZED`는 다른 상황이다. `ADMIN_LOGIN_FAILED`는 `POST /admin/auth/login` 시도 자체가 ID/PW 불일치로 실패한 경우다(아이디 존재 여부는 구분하지 않고 항상 이 코드 하나로 응답한다). `ADMIN_UNAUTHORIZED`는 이미 보호된 라우트에서 Cookie/JWT가 없거나 만료된 경우다.

`DAILY_ORDER_LIMIT_EXCEEDED`는 `order_daily_counters.last_number`가 9999를 초과하는 경우 사용한다(`002_백엔드1_주문결제.md` §11 참고).

`TOO_MANY_REQUESTS`(429, 확정 2026-09-18)는 rate limit 초과 시 사용하는 공통 fallback code다. 현재는 `POST /admin/auth/login`에만 적용되어 있다(`003_백엔드2_운영실시간.md` §7 참고). `@nestjs/throttler`의 `ThrottlerException`이 그대로 이 코드로 매핑된다.

# 21. AdminGuard 동작 계약

```text
Request
  ↓
admin_access_token Cookie 조회
  ↓
JWT 서명 검증
  ↓
JWT exp 검증
  ↓
sub → adminId
  ↓
AuthenticatedAdmin 생성
  ↓
request.admin 저장
```

성공:

```ts
request.admin = {
  adminId,
  expiresAt,
};
```

실패:

```text
401
ADMIN_UNAUTHORIZED
```

AdminGuard 구현에서 인증 실패를 처리할 때는 NestJS 기본 `UnauthorizedException`을 던지지 않는다.

`ApiException(ERROR_CODE.ADMIN_UNAUTHORIZED, ...)`처럼 명시적인 domain error code를 사용해서 응답 code가 항상 `ADMIN_UNAUTHORIZED`로 고정되도록 한다.

기본 `UnauthorizedException`을 던지면 공통 오류 필터가 이를 범용 `UNAUTHORIZED`로 처리하여 프론트가 기대하는 `ADMIN_UNAUTHORIZED` 계약과 어긋난다.

Backend 1은 관리자 API에서 동일 Guard를 사용한다.

예:

# 23. AdminAuthModule 공개 계약

Backend 2의 `AdminAuthModule`은 최소 다음을 export한다.

```text
AdminGuard

JwtModule
```

**`JwtModule`도 함께 export해야 하는 이유 (확정):** NestJS는 `@UseGuards(AdminGuard)`를 다른 모듈(Backend 1의 OrdersModule 등)에서 사용할 때, `AdminGuard`를 그 **소비 모듈의 컨텍스트**에서 새로 인스턴스화한다. 이때 `AdminGuard`의 생성자 의존성인 `JwtService`도 소비 모듈에서 해석 가능해야 하므로, `AdminAuthModule`이 `JwtModule`을 함께 export하지 않으면 `AdminGuard`를 사용하는 다른 모듈이 아예 부팅되지 않는다(`UnknownDependenciesException`). `AdminGuard`만 export하는 것으로는 부족하다.

필요한 경우:

```text
AdminAuthService
```

도 export할 수 있다.

단 Backend 1이 AdminAuthService 내부 구현이나 AdminRepository를 직접 사용하지 않는다.

# 36. Event의 의미

Event는 **상태 데이터 자체가 아니다.**

```text
PostgreSQL = 최종 상태

Event = 변경 알림

Socket.IO = 전달

REST = 최신 데이터 조회
```

Socket 이벤트가 누락돼도 DB 상태는 유지된다.

재접속 시 REST를 조회한다.


따라서 Redis/Kafka/RabbitMQ/Outbox를 현재 MVP에 추가하지 않는다.

# 38. 공통 계약 7 — Order 접근 확인 (이름 + 주문번호)

v0.9부터 Guest 쿠키/Guest 테이블을 사용하지 않는다. 고객은 항상 **이름 + 주문번호**로 자신의 주문에 접근한다 (`02_백엔드1_주문결제.md` §6~8 참고).

Realtime에서 고객이 특정 주문을 구독할 때도 REST lookup과 동일한 방식을 사용한다. Realtime이 orders 테이블 권한 로직을 따로 구현하지 않는다.

---

## OrderLookupInput

```ts
export interface OrderLookupInput {
  customerName: string;
  orderNumber: string;
}
```

---

## Backend 1 공개 서비스

개념적으로 다음 기능을 제공한다.

```ts
interface OrderAccessReader {
  findOrderForLookup(
    input: OrderLookupInput,
  ): Promise<{ orderId: string } | null>;
}
```

실제 provider 이름은 Backend 1 내부 구조에 맞춰 정해도 되지만 **의미는 동일해야 한다.** REST의 `POST /orders/lookup`과 내부적으로 같은 조회 로직을 공유한다.

---

## Realtime 사용

```text
Socket 연결
    ↓
customerName + orderNumber 제시
    ↓
Backend 1 OrderAccessReader.findOrderForLookup()
    ↓
orderId
    ↓
order room join
```

클라이언트가 보낸 `orderId`만으로는 접근 권한을 주지 않는다. `customerName` + `orderNumber`를 함께 제시해야 room에 join할 수 있다.

이 방식은 REST lookup과 동일한 신뢰 수준이다 — 이름+주문번호 조합을 아는 사람이면 조회 가능하다는 전제를 이미 받아들인 상태이므로(`02` §6 "왜 쿠키를 쓰지 않는가"), Socket 인증에서 별도로 더 강한 보장을 추가하지 않는다.

---

# 39. (해결됨) 과거 lookup 고객 Realtime 이슈

v0.6까지는 "Cookie 없는 lookup 고객의 Socket 접근 방식"이 미정 항목이었다.

v0.9부터는 Guest 쿠키 자체가 없고 **모든 고객이 이름+주문번호 방식만 사용**하므로, 이 항목은 더 이상 예외 케이스가 아니라 §38의 기본 동작 그 자체다. 별도 proof/token 발급 없이 §38의 `OrderAccessReader.findOrderForLookup()`으로 통일한다.

# 42. CORS / CSRF

**운영 환경 (확정, 2026-09-18):** Frontend와 Backend는 항상 동일 Origin으로 배포한다. Nginx Reverse Proxy가 다음과 같이 라우팅한다.

```text
/            → Next.js

/api/*       → NestJS REST

/socket.io/* → NestJS Socket.IO
```

동일 Origin이므로 관리자 Cookie는 항상 first-party Cookie다. 이에 따라 다음을 MVP 범위에서 확정한다.

```text
COOKIE_SAME_SITE=none 지원하지 않음 (env.validation이 시작 시점에 거부한다)

cross-site Cookie 인증 미지원

상태 변경 API에 대한 별도 Origin 검증/CSRF 미들웨어 구현하지 않음
(SameSite=lax/strict Cookie가 cross-site 요청에 실리지 않는 것으로 충분하다고 본다)
```

**로컬 개발 환경:** Frontend(Next.js)와 Backend(NestJS)가 서로 다른 포트로 뜨므로, `FRONTEND_ORIGIN` + `credentials: true` 기반 CORS 설정으로 처리한다(운영에서는 동일 Origin이라 CORS가 실질적으로 개입하지 않는다).

```ts
app.enableCors({
  origin: configService.get<string>('FRONTEND_ORIGIN'),
  credentials: true,
});
```

HttpOnly만으로 CSRF가 해결된 것으로 보지 않지만, 위 결정에 따라 동일 Origin 배포 + SameSite Cookie 조합을 CSRF 대응으로 채택한다. 향후 배포 형상이 교차 Origin으로 바뀌면 이 절을 다시 검토하고 별도 Origin 검증을 추가해야 한다.

# 44. SalesView

환불 정책 확정(전액 환불만, `002_백엔드1_주문결제.md` §24 참고)에 따른 구조:

```ts
  amount: number;

export interface SalesTotalsWithRefund extends SalesTotals {

  refundedAmount: number;

export interface SalesView {
  timezone: 'Asia/Seoul';

  basis: 'payment_confirmed_at';

  asOf: string;

  festivalPeriod: {
    from: string;
    to: string;

  today:
    SalesTotalsWithRefund & {
      date: string;

  festival:

  daily:
```

v0.9부터 고객은 Cookie를 사용하지 않으므로 `COOKIE_*` 환경변수는 `admin_access_token`에만 적용된다.

JWT 30분 만료는 환경변수로 임의 변경하지 않고 서비스 계약으로 고정한다.

**`ADMIN_JWT_SECRET`은 32자 미만이면 애플리케이션 시작을 거부한다 (확정, 2026-09-18).** 관리자 JWT가 유출됐을 때 오프라인 브루트포스로 서명 키가 복구되면 임의의 관리자 토큰을 위조할 수 있으므로, 길이(존재 여부뿐 아니라 최소 강도)를 시작 시점에 검증한다. `openssl rand -base64 48` 등으로 생성한 충분히 무작위한 값을 사용한다.

`DB_POOL_MAX`, `DB_CONNECTION_TIMEOUT_MS`, `DB_IDLE_TIMEOUT_MS`, `DB_STATEMENT_TIMEOUT_MS`, `DB_IDLE_TRANSACTION_TIMEOUT_MS` 같은 DB 숫자 환경변수는 애플리케이션 시작 시 숫자로 변환하고 허용 범위를 검증한다.

값을 설정했는데 정수가 아니거나 허용 범위를 벗어나면 애플리케이션 시작 자체를 실패시킨다.

잘못된 값을 무시하고 기본값으로 조용히 대체하거나 그대로 시작하지 않는다.

# 47. Migration 공통 규칙

DB Schema 변경은 SQL Migration으로 관리한다.

**파일명 규칙 (확정, 2026-09-19):** 서로 다른 브랜치에서 동시에 작업하면 번호(001, 002...)가 우연히 겹칠 수 있으므로, 파일명 앞에 담당 Backend를 표시하는 접두사를 붙인다.

```text
Backend 1: b1_
Backend 2: b2_
```

예:

```text
b2_001_create_admins.sql

b2_002_create_menus.sql

b2_003_add_menus_updated_at.sql

b2_004_create_menu_history.sql

b2_005_create_payment_settings.sql

b2_006_create_payment_settings_history.sql

b1_001_create_orders.sql

b1_002_create_order_items.sql

b1_003_create_order_daily_counters.sql

b1_004_create_order_history.sql

b1_005_create_order_refunds.sql
```

접두사가 다르면 번호가 겹쳐도 실제 파일명은 절대 겹치지 않는다. 두 Backend가 서로 번호를 맞춰볼 필요가 없다.

(위 예시는 실제 적용된 파일명 기준으로 갱신된 것이다. `payment_settings`는 애초 예상과 달리 `b2_003`이 아니라 `b2_005`를 사용했다 — menus `updated_at` 컬럼 추가와 `menu_history` 생성 migration이 먼저 그 번호들을 사용했기 때문이다. 자세한 경위는 `04_DB스키마.md` §12 참고.)

Guest 테이블이 없으므로 guests migration은 만들지 않는다.

`b1_001_create_orders.sql`은 `customer_name`, `customer_phone` 컬럼을 포함한다 (`002_백엔드1_주문결제.md` §6 참고).

같은 Backend 안에서의 순서는 번호로, FK 의존성에 따라 조정한다. `database/migrate.ts`는 파일명을 알파벳순으로 정렬해 순서대로 적용하므로 `b1_`이 `b2_`보다 항상 먼저 실행된다 — 현재는 `b1_`/`b2_` 소유 테이블 사이에 FK가 없으므로(§5, `04_DB스키마.md`) 문제가 되지 않는다. 다만 향후 `order_history.actor_id`/`order_refunds.processed_by`처럼 Backend 1 테이블이 `admins.id`를 실제 FK로 참조하게 되면, 그 시점에는 해당 Migration이 `b2_001_create_admins.sql` **이후**에 실행되도록 번호 순서를 맞춰야 한다(접두사만으로는 실행 순서가 보장되지 않는다).

# 57. 공통 테스트

최소 다음 시나리오를 실제 PostgreSQL에서 검증한다.

| 시나리오 | 확인 |
| --- | --- |
| DB Transaction | 동일 PoolClient 사용 |
| Order 실패 | 관련 INSERT 전체 Rollback |
| Menu 가격 변경 | 기존 OrderItem 가격 유지 |
| Admin 인증 | B1/B2 동일 AdminGuard |
| 관리자 만료 | REST와 Socket 모두 종료 |
| 동일 주문 요청 | 주문 한 건만 생성 |
| 입금 vs 취소 | 하나만 성공 |
| Event | COMMIT 이후만 발생 |
| Socket 누락 | REST 최신 조회로 복구 |
| 타인 주문 | 조회/Socket 구독 모두 차단 |
| 매출 자정 | KST payment_confirmed_at 기준 |

메모리 mock만으로 PostgreSQL 동시성이나 Lock 동작을 검증했다고 판단하지 않는다.

# 59. 공통 구현 완료 기준

다음이 모두 충족되면 공통 Backend 기반이 준비된 것으로 본다.

- 하나의 PostgreSQL Pool만 사용한다.
- Transaction 전체가 같은 PoolClient에서 실행된다.
- 공통 OrderStatus를 사용한다.
- DTO ValidationPipe가 적용된다.
- Error 응답 형식이 동일하다.
- 관리자 인증 principal 형식이 동일하다.
- Backend 1이 Backend 2의 AdminGuard를 사용할 수 있다.
- Backend 1이 MenuReader를 같은 Transaction client로 사용할 수 있다.
- Orders와 Realtime이 직접 의존하지 않는다.
- OrderEventPublisher로 이벤트를 발행한다.
- 이벤트는 DB COMMIT 이후에만 발생한다.
- Realtime은 Event를 전달할 뿐 Order를 변경하지 않는다.
- 공통 Migration 규칙을 따른다.
- `.env`가 Git에 포함되지 않는다.
- 공통 계약을 각 도메인에 복제하지 않는다.
