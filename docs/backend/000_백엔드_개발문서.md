# 4. 모듈 설계 원칙

NestJS Feature Module을 도메인 경계로 사용한다.

```text
Controller
    ↓
Service
    ↓
Repository
    ↓
PostgreSQL
```

Controller는 HTTP 입력/응답을 담당한다.

Service는 업무 규칙을 담당한다.

Repository는 SQL 실행을 담당한다.

다른 도메인이 필요한 기능은 내부 Repository에 직접 접근하지 않고 해당 Module이 export한 Service 또는 명시적으로 공개한 provider를 사용한다.

예:

```text
OrdersModule
    │
    ├── MenusModule이 공개한 MenuQuery 사용
    ├── AdminAuthModule이 공개한 AdminGuard 사용
    └── 공통 DomainEventPublisher 사용
```

# 5. 구현 참고 패턴

이번 구현은 다음 검증된 구조를 참고한다.

## NestJS Auth 패턴

NestJS 공식 JWT 예제 구조를 따라 다음처럼 분리한다.

```text
AdminAuthController
AdminAuthService
JwtService
AdminGuard
AdminsRepository
```

JWT는 응답 body나 localStorage에 저장하지 않고 HttpOnly Cookie를 사용한다.

---

## NestJS Module 패턴

상대 도메인이 필요한 기능만 `exports`한다.

예:

```ts
@Module({
  providers: [MenusService, MenusRepository],
  controllers: [MenusController],
  exports: [MenusService],
})
export class MenusModule {}
```

Repository 자체를 무조건 공개하지 않는다.

---

## PostgreSQL / pg 패턴

애플리케이션 전체에서 하나의 Pool을 사용한다.

단일 조회:

```text
pool.query()
```

Transaction:

```text
pool.connect()
    ↓
BEGIN
    ↓
같은 client로 모든 SQL
    ↓
COMMIT / ROLLBACK
    ↓
client.release()
```

Transaction 내부에서 `pool.query()`로 빠져나가지 않는다.

---

## 실시간 패턴

Socket.IO를 DB 원장으로 사용하지 않는다.

```text
DB 변경
  ↓
COMMIT
  ↓
이벤트 발생
  ↓
Socket 전달
  ↓
클라이언트 REST 재조회
```

현재 MVP에서는 한 개의 NestJS 프로세스를 기준으로 in-process event를 사용한다.

Redis / Kafka / RabbitMQ는 사용하지 않는다.

# 8. 도메인 간 계약

## AdminAuth → Orders

Backend 2가 제공한다.

```text
AdminGuard
AuthenticatedAdmin
```

Backend 1의 관리자 주문 API는 동일 Guard를 사용한다.

---

## Menu → Orders

Backend 2가 메뉴 조회 기능을 제공한다.

```ts
getMenuSnapshots(
  client: PoolClient,
  menuIds: string[],
): Promise<MenuSnapshot[]>
```

Backend 1은 주문 Transaction 안에서 이 함수를 이용한다.

메뉴 가격이나 품절 상태를 직접 수정하지 않는다.

---

## Orders → Realtime

Backend 1이 DB COMMIT 이후 이벤트를 발생시킨다.

```text
order.created
order.updated
```

Backend 2가 해당 이벤트를 Socket.IO로 전달한다.

---

## Orders → Sales

Backend 2의 Sales는 주문 데이터를 읽어서 계산한다.

Backend 1은 컬럼 의미와 테스트 fixture를 보장한다.

# 10. 공통 응답 기준

성공 응답의 세부 래퍼는 구현 전 프론트와 확정한다.

오류는 최소 다음 형태로 통일한다.

```json
{
  "code": "ORDER_STATE_CONFLICT",
  "message": "현재 주문 상태에서는 처리할 수 없습니다."
}
```

대표 오류:

```text
VALIDATION_ERROR
MENU_UNAVAILABLE
IDEMPOTENCY_CONFLICT
ORDER_NOT_FOUND
ADMIN_UNAUTHORIZED
SALES_PASSWORD_INVALID
ORDER_STATE_CONFLICT
```

# 11. 입력 검증

NestJS DTO + ValidationPipe를 사용한다.

권장 공통 설정:

```ts
new ValidationPipe({
  whitelist: true,
  forbidNonWhitelisted: true,
  transform: true,
})
```

클라이언트가 보낸 다음 값은 신뢰하지 않는다.

```text
가격
총금액
adminId body 값
Order actor
주문 상태
```

서버가 DB와 인증 정보로 결정한다.

# 12. 통합 테스트 시나리오

최소 다음 시나리오를 실제 PostgreSQL에서 검증한다.

### 정상 주문

```text
메뉴 조회
→ 주문 생성 (이름 + 전화번호 입력)
→ 주문번호
→ 이름 + 주문번호 조회
→ 입금 확인
→ COOKING
→ READY
→ COMPLETED
```

### 중복 요청

```text
동일 orderRequestId 동시 요청
→ 주문 1건만 생성
```

### 상태 경합

```text
입금 확인
vs
CANCELLED

→ 한쪽만 성공
```

### 메뉴 변경

```text
주문 생성
→ 메뉴 가격 변경
→ 기존 주문 가격 유지
→ 새 주문에 새 가격 적용
```

### Socket 복구

```text
Socket 연결 종료
→ 주문 상태 변경
→ 재접속
→ REST 최신 조회
```

### 관리자 만료

```text
로그인
→ 30분
→ REST 차단
→ 기존 관리자 Socket도 차단
```

### 자정 매출

```text
23:58 주문
00:01 입금 확인
→ 다음 날짜 매출
```
