# 7. 관리자 로그인

흐름:

```text
username / password
        ↓
admins 조회
        ↓
password_hash 검증
        ↓
JWT 생성
        ↓
HttpOnly Cookie
```

JWT 만료:

```text
12시간
```

Refresh Token은 사용하지 않는다.

**로그인 실패 (확정):** 아이디가 없는 경우와 비밀번호가 틀린 경우를 구분하지 않고 항상 `ADMIN_LOGIN_FAILED`(401) 하나로 응답한다(계정 존재 여부 노출 방지). 성공 응답은 `204 No Content`로 Cookie만 설정하고 body는 없다.

**로그인 Rate Limit (확정, 2026-09-18):** `POST /admin/auth/login`에는 IP당 60초에 10회로 제한을 건다. 축제 운영자 수가 적은 이번 프로젝트 규모에 맞춘 최소한의 방어이며, `@nestjs/throttler`의 기본 in-memory storage를 그대로 사용한다(Redis 등 별도 인프라를 추가하지 않는다). 초과 시 `429 TOO_MANY_REQUESTS`(메시지: "요청이 너무 많습니다. 잠시 후 다시 시도해 주세요.")로 응답한다(공통 fallback code, `001_백엔드_공통.md` §18 참고). 동일 Origin 배포(Nginx Reverse Proxy, §36 참고) 환경에서 IP를 정확히 식별하려면 Express `trust proxy` 설정이 필요하며 `main.ts`에서 처리한다.

`@nestjs/throttler`의 `ThrottlerModule`은 라이브러리 특성상 `@Global()`이라 `app.module.ts`에서 한 번만 `forRoot()`로 등록한다(도메인 모듈 안에서 등록하면 나중에 다른 모듈이 또 등록했을 때 어느 설정이 적용될지 모듈 import 순서에 좌우되는 문제가 생긴다). 이 default profile을 직접 쓰는(`@UseGuards(ThrottlerGuard)`) 라우트는 `POST /admin/auth/login` 하나이고, `POST /admin/sales/query`는 같은 profile을 재사용하되 tracker만 IP에서 adminId로 바꾼 서브클래스 `SalesThrottlerGuard`를 쓴다(§19 참고, NAT 공유 환경 대응). 배포 시 `trust proxy`/Nginx 설정이 실제로 맞물려 동작하는지는 `11_배포_체크리스트.md` §1~2를 따라 확인한다.

```text

   ↓

   ↓

   ↓
```

# 10. 로그아웃

로그아웃은 관리자 Cookie를 삭제한다.

발급할 때 사용한:

```text
name
Domain
Path
SameSite
Secure
```

옵션과 삭제 옵션을 맞춘다.

**AdminGuard 미적용 (확정):** `POST /admin/auth/logout`에는 AdminGuard를 걸지 않는다. Cookie가 없거나 JWT가 만료·변조된 상태로 호출해도 `ADMIN_UNAUTHORIZED`를 반환하지 않고, 항상 Cookie를 삭제하고 `204`로 응답하는 멱등적 동작으로 구현한다.

**구현됨 (Step 6, 세션 단위로 정정 2026-09-20):** 현재 브라우저(=이 로그인 세션)의 관리자 Socket만 종료한다. 로그아웃 요청의 Cookie가 유효한 JWT일 때만 그 JWT의 `jti`(로그인 세션 식별자)와 일치하는 Socket을 즉시 끊는다(`admin.logged_out` 이벤트로 AdminAuth → Realtime에 `{ adminId, sessionId }`를 전달, EventEmitter2). 같은 adminId로 다른 기기/탭에서 로그인한 Socket은 `jti`가 다르므로 영향받지 않는다 — 공유 기기(아이패드 등)에서 여러 관리자가 번갈아 로그인하거나, 한 관리자가 여러 기기에서 동시에 로그인해 있어도 한쪽 로그아웃이 다른 쪽 세션에 영향을 주지 않는다. Cookie가 없거나 만료·변조된 상태라면 어떤 세션인지 신뢰할 수 없으므로 Socket 종료는 시도하지 않는다 — 로그아웃 자체(Cookie 삭제, 204)는 이 경우에도 항상 멱등적으로 동작한다. 서버는 "현재 로그인된 세션 목록"을 별도로 저장하지 않는다 — JWT 자체에 실린 `jti` 값을 비교할 뿐이다.

JWT 자체의 서버 블랙리스트는 현재 구현하지 않는다. 즉 만료 전 탈취 시 즉시 무효화는 안 되며, 이 노출 구간은 JWT 유효기간과 같은 최대 12시간이다. 이를 감수한다(확정, 2026-09-20).

**알려진 제약:** 같은 기기에서 로그아웃 없이(예: 로그아웃 버튼을 거치지 않고 Cookie만 지우거나 앱을 강제 종료한 뒤) 재로그인하면, 이전 세션의 Socket 연결이 곧바로 끊기지 않고 남아 있을 수 있다. 이전 세션의 JWT 자체는 만료 전까지 여전히 유효한 토큰이므로 새로 발생하는 보안 위험(권한 상승, 인증 우회 등)은 없다 — 다만 그 세션은 로그아웃 신호를 받지 못했을 뿐이며, 실제로는 JWT 만료(최대 12시간) 시 함께 종료된다.

# 11. Menu

menus는 현재 메뉴 상태의 기준이다.

필드:

```text
id
name
price
is_available
```

메뉴 사진(이미지)은 현재 필드/API에 포함하지 않는다. 저장 방식(서버 로컬 디스크)과 CDN 계획은 확정되었으나 실제 구현은 Step 11(Oracle 배포) 시점으로 보류했다 — `11_배포_체크리스트.md` §5 참고.

**메뉴 변경 이력 (확정, 2026-09-19):** `PATCH /admin/menus/:menuId`로 `price`/`is_available`이 **실제로** 바뀔 때마다 `menu_history`에 변경 전/후 값, 변경한 관리자(`admin_id`), 시각(`changed_at`)을 남긴다. 값이 같은 no-op PATCH는 기록하지 않는다. `menus` UPDATE와 `menu_history` INSERT는 하나의 Transaction으로 처리되어, 한쪽만 성공하는 상태가 생기지 않는다. 상세 스키마와 흐름은 `04_DB스키마.md` §8-1 참고. 이번 단계에서는 이 이력을 읽는 조회 API는 만들지 않는다(DB 내부 감사 기록용).

# 19. Sales 접근 인증

매출 페이지에서는 현재 로그인한 관리자의 비밀번호를 다시 입력한다.

흐름:

```text
AdminGuard
    ↓
현재 adminId
    ↓
사용자 입력 password
    ↓
verifyAdminPassword()
    ↓
성공
    ↓
Sales 조회
```

API:

```http
POST /admin/sales/query
```

별도 Sales JWT는 만들지 않는다.

별도 Sales Cookie도 만들지 않는다.

비밀번호 검증 성공 상태를 시간 단위로 유지하지 않는다.

**Rate limit (확정, Sales Step 9 구현 시 반영):** `POST /admin/sales/query`도 매 요청마다 argon2 비밀번호 재검증을 하므로 `POST /admin/auth/login`과 동일한 brute-force 방어가 필요하다. 다만 로그인과 똑같이 IP 기준으로 세면, 축제 현장처럼 여러 운영자가 같은 Wi-Fi/NAT(=같은 공인 IP)을 쓰는 환경에서 한 운영자의 비밀번호 오타가 같은 IP를 쓰는 다른 운영자의 정상적인 매출 조회까지 막아버릴 수 있다(2차 리뷰 확정, 2026-09-20). 그래서 이 라우트에는 기본 `ThrottlerGuard`(IP 기준) 대신 `SalesThrottlerGuard`(`backend/src/sales/sales-throttler.guard.ts`)를 쓴다 — `ThrottlerGuard.getTracker()`를 오버라이드해 `request.admin.adminId`(AdminGuard가 먼저 채워 둠)를 tracker로 쓰고, adminId를 알 수 없는 경우(정상적으로는 발생하지 않지만 방어적으로)에만 IP로 fallback한다. 제한 횟수/기간(IP당이 아니라 이제 admin당 60초 10회) 자체는 `POST /admin/auth/login`용 `ThrottlerModule` default profile(`admin-auth-rate-limit.ts`)을 그대로 재사용한다 — `ThrottlerGuard`(및 그 서브클래스)는 Controller+Handler 단위로 카운터를 따로 추적하므로, 같은 profile을 재사용해도 두 라우트의 시도 횟수는 서로 섞이지 않는다. 새로운 named throttler profile은 추가하지 않는다(라우트마다 `@SkipThrottle()`을 세심하게 지정해야 해서 복잡도만 올라간다). `/admin/auth/login`은 로그인 전이라 adminId 자체를 모르므로 `SalesThrottlerGuard`를 적용하지 않고 기존 `ThrottlerGuard`(IP 기준)를 그대로 쓴다.

# 22. JOIN 중복 주의

다음처럼 Order + Items + Refunds를 무조건 한 번에 JOIN하면 행이 곱해질 수 있다.

따라서 필요한 단위별로 먼저 집계한다.

원 결제 기본 집계 예:

```sql
SELECT
  COALESCE(SUM(oi.quantity), 0)::integer AS quantity,
  COALESCE(
    SUM(oi.unit_price * oi.quantity),
    0
  )::integer AS amount

FROM orders o

JOIN order_items oi
  ON oi.order_id = o.id

WHERE o.payment_confirmed_at >= $1
  AND o.payment_confirmed_at < $2;
```

**`::bigint`가 아니라 `::integer`를 쓰는 이유 (확정, Sales Step 9 구현 시 반영):** `SUM(integer 컬럼)`의 PostgreSQL 결과 타입은 `bigint`(OID 20)인데, `pg` 드라이버는 정밀도 손실을 막기 위해 `bigint`를 JS `number`가 아니라 **문자열**로 반환한다. 캐스팅하지 않으면 `SalesView.amount`/`quantity`가 숫자가 아닌 문자열로 응답에 섞여 계약을 깬다. 학교 축제 규모의 매출은 2^31(약 21억 원)을 넘을 수 없고 `orders.total_price`도 이미 `INTEGER`이므로, `SUM` 결과를 다시 `::integer`로 좁혀도 안전하다. 실제 구현은 `backend/src/sales/sales.repository.ts` 참고.

# 24. Refund와 Sales

환불 자체는 Backend 1이 기록한다(`order_refunds`, 전액 환불만 지원, 주문당 1건).

Backend 2는 해당 기록을 읽는다.

**최종 확정 정책 (2026-09-18, Sales Step 9 구현 시 재확인):**

```text
환불은 원 주문에 귀속된다 — 원 주문(orders)과 원 주문 항목(order_items) 스냅샷,
  결제 금액(total_price)과 payment_confirmed_at은 환불 여부와 무관하게 수정하지 않는다.
어떤 주문이 환불됐는지는 주문 자체가 아니라 그 주문의 환불 기록(order_refunds)으로 추적한다.
Sales의 refundedAmount는 결제일(payment_confirmed_at)이 아니라
  실제 환불 처리일(order_refunds.processed_at) 기준으로 그 날짜 통계에 집계한다
  — 결제일과 환불 처리일은 다를 수 있다(예: 9/20 결제, 9/21 환불 처리 → refundedAmount는 9/21 통계에 표시).
전액 환불만 지원 (부분 환불 없음)
메뉴별 환불 배분 없음 (byMenu에는 refundedAmount를 포함하지 않는다) — 이 정책은
  Backend 1 order_refunds 연동 이후에도 계속 유지한다(전액 환불만 지원하므로
  메뉴별로 나눌 근거 자체가 없다).
```

`amount`(원 결제액)는 환불 여부와 무관하게 그대로 유지한다. 순매출이 필요하면 `amount - refundedAmount`를 프론트엔드에서 계산한다(백엔드는 순매출 필드를 별도로 만들지 않는다). 상세 타입은 `001_백엔드_공통.md` §44 `SalesView` 참고.

## 24-1. 현재 구현 상태 (Step 9 완료, Step 10 대기)

**현재 구현 상태:** `POST /admin/sales/query`(Sales 기본 집계, Step 9)는 구현되어 있다. 하지만 이 시점 기준 Backend 1의 `order_refunds` 테이블/환불 기능(`POST /admin/orders/:orderId/refunds`)이 아직 구현되지 않았다. 환불 정책 자체는 이미 확정되었지만(위 §24, `04_DB스키마.md` §5) 실제로 집계할 테이블/데이터가 아직 없다.

이 상태에서 Sales가 막히지 않도록, `refundedAmount` 집계만 다음 위치에 격리했다.

```text
backend/src/sales/refund-aggregation.service.ts
  → RefundAggregationService.getRefundedAmount(range): Promise<number>
```

- 현재는 항상 `0`을 반환하는 자리표시(placeholder) 구현이다. 버그가 아니라 의존 기능(`order_refunds`) 미구현에 따른 의도된 임시 동작이며, `test/unit/sales/refund-aggregation.service.spec.ts`가 이 사실을 테스트로 문서화한다.
- `SalesView` 응답 계약(`refundedAmount` 필드 자체)은 이 임시 구현과 무관하게 그대로 유지된다 — Frontend는 처음부터 이 필드를 받는다.
- `byMenu`에는 `refundedAmount`를 넣지 않는 정책(§24)은 이 임시 구현과 무관하게 최종 정책이며, Backend 1 연동 이후에도 유지한다.

**Step 10(Backend 1 Refund 연동) 착수 시 해야 할 일:**

1. `order_refunds.processed_at` 기준으로 `RefundAggregationService.getRefundedAmount(client, range)`의 본문만 실제 집계 쿼리로 교체한다(메서드 시그니처는 유지 — 호출부인 `SalesService`는 변경할 필요가 없다). `client`는 `SalesService`가 이미 열어 둔 REPEATABLE READ READ ONLY 트랜잭션의 `PoolClient`이므로, 반드시 이 `client`로 쿼리해야 한다(아래 "집계 일관성" 참고 — 별도 Pool 연결을 쓰면 같은 요청의 `amount`/`quantity` 집계와 다른 스냅샷을 볼 수 있다).
2. `refund-aggregation.service.spec.ts`의 "항상 0" 검증을 실제 집계값 검증으로 교체한다.
3. 위 Sales 테스트 체크리스트의 "Refund 정책 확정 후 환불 집계 일치" 항목을 검증하고 체크한다.
4. 아래 "daily의 구조적 한계"를 함께 처리한다.

**`daily`의 구조적 한계 (TODO, Step 10에서 함께 처리):** 현재 `daily`는 `payment_confirmed_at`(결제일) 기준으로 `GROUP BY`해 행을 만든다(`sales.repository.ts`의 `getDailyBreakdown()`). 즉 "그 날짜에 결제 확인된 주문이 최소 1건 이상 있어야" `daily` 배열에 그 날짜 행이 생긴다. Backend 1의 환불이 실제로 연동되면, "그 날짜에 결제는 0건이지만 환불(처리)만 발생한 날짜"가 있을 수 있는데(예: 축제 마지막 날 이후 환불 처리), 이런 날짜는 지금 구조상 `daily`에 행 자체가 생기지 않아 그 날의 `refundedAmount`를 보여줄 자리가 없다. Step 10에서 `daily`의 날짜 집합을 "결제일이 있는 날짜 ∪ 환불 처리일이 있는 날짜"로 합치도록 `getDailyBreakdown()`(또는 `SalesService`의 조립 로직)을 확장해야 한다. 지금 단계에서는 이 케이스를 억지로 구현하지 않는다(어차피 `refundedAmount`가 항상 0이라 관찰할 수도 없다) — `SalesView` 응답 계약 자체(필드 이름/타입)는 이 작업으로 바뀌지 않는다.

**집계 일관성 (REPEATABLE READ 스냅샷, 확정, Sales Step 9 구현 시 반영):** 한 매출 조회 요청 안에서 today/festival/daily/byMenu 5개 집계 쿼리(+ 환불 집계)를 서로 다른 Pool 커넥션으로 각각 실행하면, 요청 처리 도중 다른 트랜잭션이 새로 COMMIT한 입금 확인이 일부 쿼리에만 반영되고 다른 쿼리에는 반영되지 않아 응답 안에서 숫자가 서로 어긋날 수 있다. PostgreSQL 기본 격리 수준(READ COMMITTED)은 트랜잭션이 아니라 각 개별 문장 단위로 스냅샷을 새로 잡으므로, 단순히 `BEGIN`/`COMMIT`으로 감싸는 것만으로는 이 문제를 막지 못한다. `SalesService.query()`는 하나의 `DatabaseService.withTransaction()` 트랜잭션을 열고, 그 안에서 가장 먼저 `SET TRANSACTION ISOLATION LEVEL REPEATABLE READ, READ ONLY`(`sales/sales-snapshot.ts`의 `useRepeatableReadSnapshot()`)를 실행해 트랜잭션 시작 시점 스냅샷을 고정한 뒤, 모든 집계를 그 스냅샷 위에서 실행한다. 읽기 전용 트랜잭션이므로 write skew로 인한 직렬화 실패(재시도 필요)는 발생하지 않는다. `SalesRepository`/`RefundAggregationService`의 각 메서드가 `PoolClient`를 첫 인자로 받는 이유가 이것이다(같은 트랜잭션의 같은 커넥션을 강제하기 위함) — `DatabaseService.query()`(별도 Pool 커넥션)를 이 안에서 쓰지 않는다.

**`orders.payment_confirmed_at` 인덱스 (Backend 1과의 후속 통합/성능 검토 항목, 지금은 추가하지 않음):** Sales의 모든 집계 쿼리(`sales.repository.ts`)가 `orders.payment_confirmed_at` 범위 조건으로 `orders`를 필터링한 뒤 `order_items`와 JOIN한다. `orders`는 Backend 1 소유 테이블이므로 Backend 2(Sales) 작업에서 임의로 인덱스 Migration을 추가하지 않는다(도메인 침범 금지, §3). 축제 규모(학교 축제, 소량 주문)에서는 순차 스캔으로도 문제가 없을 가능성이 높지만, 실제 배포 후 주문량과 쿼리 플랜을 보고 필요하면 Backend 1이 `orders.payment_confirmed_at`(또는 `(payment_confirmed_at)` 부분 인덱스 등)에 인덱스를 추가하는 Migration을 만드는 것을 후속 검토 항목으로 남긴다. 자세한 내용은 `002_백엔드1_주문결제.md` §24(매출 반영) 하단의 같은 항목 참고.

# 30. 고객 Socket 인증

v0.9부터 고객은 Cookie를 사용하지 않는다. 모든 고객은 이름+주문번호로 REST lookup(`POST /orders/lookup`)한 것과 동일한 방식으로 Socket도 인증한다.

```text
Socket
  ↓
customerName + orderNumber 제시
  ↓
Backend 1 OrderAccessReader.findOrderForLookup()
  ↓
orderId
  ↓
order:{id} join
```

클라이언트가 `orderId`만 안다고 해서 구독을 허용하지 않는다. `customerName` + `orderNumber`를 함께 제시해야 한다.

**전달 프로토콜 (확정):** 별도의 구독 emit 이벤트 없이, Socket.IO 연결의 `auth` 옵션으로 연결 시점에 함께 제시한다(`io(url, { auth: (cb) => cb({ customerName, orderNumber }) })`). 서버는 `io.use()` handshake 미들웨어에서 이 값을 검증하고, 실패하면 연결 자체를 거절한다. 재연결 시에도 클라이언트가 같은 값을 자동으로 다시 보낸다. 상세 예시는 `03_API명세서.md` §3-4 참고.

# 31. (해결됨) 과거 lookup 고객 미정 항목

v0.8까지는 "Cookie 없는 lookup 고객의 Socket 접근 방식"이 미정이었다.

# 36. Reverse Proxy

**확정 (2026-09-18):** Nginx를 사용하며, 다음 경로 기준으로 라우팅한다(Frontend/Backend 동일 Origin).

```text
/            → Next.js

/api/*       → NestJS REST

/socket.io/* → NestJS Socket.IO
```

구조:

```text
Internet
   ↓
HTTPS
   ↓
Nginx Reverse Proxy
   ├── /            → Next.js
   ├── /api/*       → NestJS REST
   └── /socket.io/* → NestJS Socket.IO
```

PostgreSQL은 인터넷에 직접 공개하지 않는다.

동일 Origin 배포이므로 관리자 Cookie는 `COOKIE_SAME_SITE=lax`(또는 `strict`)로 충분하며, cross-site Cookie 인증(`SameSite=none`)은 지원하지 않는다(`001_백엔드_공통.md` §42 참고).

현재 API 명세(`03_API명세서.md`)의 경로는 `/api` 접두사 없이 정의되어 있다(`POST /admin/auth/login` 등). 따라서 Nginx가 `/api/*`를 NestJS로 전달할 때 `/api` 접두사를 벗겨서(rewrite) 전달하거나, NestJS에 `/api` 전역 prefix를 붙여 명세와 실제 경로를 맞추는 방법 중 하나를 Step 11(Oracle 배포) 단계에서 확정한다. 이번 AdminAuth 구현은 이 결정과 무관하게 동작한다.

실제 서버에 이 구조를 적용할 때 빠뜨리기 쉬운 설정(Nginx의 `X-Forwarded-For`, NestJS `trust proxy`, NestJS 포트 직접 노출 차단 등)은 `11_배포_체크리스트.md`에 체크리스트로 정리되어 있다. Step 11 착수 시 그 문서를 기준으로 확인한다.

# 37. 프로세스 구조

현재 Realtime 이벤트가 process-local이므로 MVP에서는 단일 NestJS 프로세스를 기본으로 한다.

다음 구조를 임의로 사용하지 않는다.

```text
Nest Process 1
Nest Process 2
Nest Process 3
```

여러 프로세스를 사용할 경우 Socket.IO adapter 및 process 간 event 전달 문제가 생기므로 별도 설계가 필요하다.

Redis를 도입하지 않는 현재 MVP에서는 single process가 기본이다.

## Step 10 — Refund Sales 반영

# 42. 완료 기준

Backend 2 완료 조건:

- 관리자 로그인/JWT/Guard가 동작한다.
- Backend 1이 같은 Guard를 재사용한다.
- Menu 가격·품절 수정이 동작한다.
- Backend 1 주문 생성이 MenuSnapshot을 사용한다.
- PaymentSettings가 DB 현재값을 유지한다.
- Sales가 읽기 전용으로 집계된다.
- 매출 요청마다 관리자 PW를 재검증한다.
- Realtime이 주문을 수정하지 않고 이벤트만 전달한다.
- 다른 고객의 주문 이벤트가 노출되지 않는다.
- 관리자 JWT 만료 후 기존 Socket 접근도 종료된다.
- 재연결 후 REST로 최신 상태가 복구된다.
- Oracle HTTPS 환경에서 REST/Cookie/Socket이 모두 정상 동작한다.
- 실제 모바일 주문 흐름을 통과한다.
