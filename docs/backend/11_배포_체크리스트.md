# 배포 체크리스트

> v0.1 · 2026-09-18

이 문서는 Oracle Cloud Ubuntu 서버에 실제로 배포하기 전에 빠뜨리기 쉬운 설정을 체크리스트 형태로 모은 것이다.

전체 배포 방향(Nginx 확정, 동일 Origin, 경로별 라우팅)은 이미 `003_백엔드2_운영실시간.md` §35~37에서 확정되어 있다. **이 문서는 그 결정을 서버에 실제로 적용할 때 확인할 항목만 다루며, 배포 형상 자체를 바꾸는 결정은 하지 않는다.** 배포 방향을 바꿔야 한다면 `003_백엔드2_운영실시간.md` / `001_백엔드_공통.md`를 먼저 수정한다.

Step 11(Oracle 배포) 착수 시 이 문서를 기준으로 확인하고, 항목이 늘어나면 이 문서에 추가한다.

---

# 1. Reverse Proxy / 클라이언트 IP 식별

배경: `POST /admin/auth/login`에는 IP당 60초 10회 rate limit이 걸려 있다(`003_백엔드2_운영실시간.md` §7, `backend/src/admin-auth/admin-auth-rate-limit.ts`). 이 제한이 의미가 있으려면 NestJS가 실제 클라이언트 IP를 정확히 알아야 한다.

- [ ] **Nginx가 NestJS로 프록시할 때 `X-Forwarded-For`를 설정한다.**

  ```nginx
  proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
  proxy_set_header X-Forwarded-Proto $scheme;
  ```

  `$proxy_add_x_forwarded_for`를 써야 기존 체인에 실제 클라이언트 IP를 추가하는 방식으로 동작한다(단순 `$remote_addr`만 쓰면 다중 hop 환경에서 체인이 끊긴다). 지금은 Nginx가 Reverse Proxy의 유일한 hop이므로(`003` §36) 문제되지 않지만, 나중에 CDN 등이 앞단에 추가되면 이 설정도 다시 확인해야 한다.

- [ ] **NestJS(`main.ts`)의 `app.set('trust proxy', 1)`이 배포 환경에 적용되어 있다.** (코드에는 이미 반영되어 있음 — 실제로 서버에 배포된 빌드에 포함됐는지만 확인) `1`은 "가장 가까운 프록시 hop(Nginx) 하나만 신뢰"를 의미한다. Nginx와 NestJS 사이에 다른 프록시(로드밸런서 등)가 추가되면 이 숫자를 재검토해야 한다.

- [ ] **NestJS 포트(기본 3001)가 인터넷에 직접 노출되지 않는다.**
  `trust proxy`가 켜진 상태에서 NestJS 포트가 외부에 그대로 열려 있으면, 공격자가 `X-Forwarded-For` 헤더를 요청마다 다른 값으로 바꿔 보내는 것만으로 로그인 rate limit을 완전히 우회할 수 있다(Nginx를 거치지 않고 직접 요청하면서 신뢰할 수 없는 IP를 자칭할 수 있기 때문).
  - 확인 방법: 서버 외부에서 `curl http://<서버 공인 IP>:3001/...`을 호출했을 때 응답이 없어야 한다.
  - 조치: 방화벽(Security List/iptables)에서 3001 포트를 외부에 막거나, NestJS를 `127.0.0.1`에만 바인딩한다.

# 2. 로그인 Rate Limit 실동작 검증

- [ ] 서로 다른 클라이언트(예: 사무실 Wi-Fi와 모바일 핫스팟처럼 IP가 다른 두 네트워크)에서 각각 로그인을 반복 시도했을 때, 한쪽이 `429`를 받아도 다른 쪽은 영향받지 않는지 확인한다.
- [ ] 같은 클라이언트가 60초 안에 10회를 초과해 시도하면 실제로 `429 TOO_MANY_REQUESTS`가 오는지 확인한다.
  - 만약 정상적인 사용자가 소수의 재시도만으로도 쉽게 차단된다면, §1의 `X-Forwarded-For` 설정이 누락되어 전체 사용자가 Nginx의 IP 하나로 묶여 집계되고 있는 것일 수 있다 — 이 경우 §1을 먼저 확인한다.
- [ ] `429` 응답 body가 `{"code":"TOO_MANY_REQUESTS","message":"요청이 너무 많습니다. 잠시 후 다시 시도해 주세요."}` 형태로 오는지 확인한다.

# 3. 환경변수

- [ ] `ADMIN_JWT_SECRET`이 32자 이상의 충분히 무작위한 값인지 확인한다(`openssl rand -base64 48` 등으로 생성, `001_백엔드_공통.md` §46 참고). 짧거나 예측 가능한 값이면 앱이 아예 시작되지 않는다(`env.validation.ts`).
- [ ] `COOKIE_SECURE=true`, `COOKIE_SAME_SITE=lax`(또는 `strict`)로 설정되어 있는지 확인한다. HTTPS 배포이므로 `COOKIE_SECURE=false`로 두면 안 된다.
- [ ] `NODE_ENV=production`인지 확인한다.
