# 배포 체크리스트

> v0.2 · 2026-09-19

이 문서는 Oracle Cloud Ubuntu 서버에 실제로 배포하기 전에 빠뜨리기 쉬운 설정을 체크리스트 형태로 모은 것이다.

전체 배포 방향(Nginx 확정, 동일 Origin, 경로별 라우팅)은 이미 `003_백엔드2_운영실시간.md` §35~37에서 확정되어 있다. **이 문서는 그 결정을 서버에 실제로 적용할 때 확인할 항목만 다루며, 배포 형상 자체를 바꾸는 결정은 하지 않는다.** 배포 방향을 바꿔야 한다면 `003_백엔드2_운영실시간.md` / `001_백엔드_공통.md`를 먼저 수정한다.

Step 11(Oracle 배포) 착수 시 이 문서를 기준으로 확인하고, 항목이 늘어나면 이 문서에 추가한다.

# 0. 배포 전 필수 Seed — PaymentSettings

**배경 (2026-09-19):** `payment_settings`는 행이 없는 상태를 정상적인 "미설정" 상태로 허용하며, 이 경우 `GET /settings/payment`/`GET /admin/settings/payment`는 `404 NOT_FOUND`를 반환한다(`03_API명세서.md` §2-1, §3-3, `04_DB스키마.md` §9 참고). 계좌이체가 유일한 결제 수단이므로, 배포 시 이 seed를 빠뜨리면 **주문 자체는 정상 생성되지만 모든 고객의 입금 안내 화면이 오류가 되어 사실상 결제가 불가능해진다.**

- [ ] `npm run migrate` 실행 후, 서비스를 열기 전에 반드시 `npm run seed:payment-settings`를 실행한다.
  - 필요 환경변수: `PAYMENT_SETTINGS_SEED_BANK_NAME`, `PAYMENT_SETTINGS_SEED_ACCOUNT_NUMBER`, `PAYMENT_SETTINGS_SEED_ACCOUNT_HOLDER` (`.env.example` 참고, 앱 런타임에는 사용하지 않는 seed 전용 변수).
  - 이미 계좌가 설정되어 있으면 이 스크립트는 아무 것도 바꾸지 않는다(재실행 안전, `001_백엔드_공통.md` §48).
- [ ] 서비스를 열기 직전, `GET /settings/payment`를 실제로 호출해 `200`과 함께 올바른 계좌 정보가 오는지 확인한다(`404`가 오면 seed가 누락된 것이다).
- [ ] 관리자 화면에서 `GET /admin/settings/payment`로 계좌를 재확인하고, 필요하면 `PATCH /admin/settings/payment`로 실제 운영 계좌로 갱신한다(이후 변경은 `payment_settings_history`에 감사 기록이 남는다, `04_DB스키마.md` §9-1).

# 1. Reverse Proxy / 클라이언트 IP 식별

배경: `POST /admin/auth/login`에는 IP당 60초 10회 rate limit이 걸려 있다(`003_백엔드2_운영실시간.md` §7, `backend/src/admin-auth/admin-auth-rate-limit.ts`). 이 제한이 의미가 있으려면 NestJS가 실제 클라이언트 IP를 정확히 알아야 한다.

- [ ] **Nginx가 NestJS로 프록시할 때 `X-Forwarded-For`를 설정한다.**

  ```nginx
  proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
  proxy_set_header X-Forwarded-Proto $scheme;
  ```

  `$proxy_add_x_forwarded_for`를 써야 기존 체인에 실제 클라이언트 IP를 추가하는 방식으로 동작한다(단순 `$remote_addr`만 쓰면 다중 hop 환경에서 체인이 끊긴다). 지금은 Nginx가 Reverse Proxy의 유일한 hop이므로(`003` §36) 문제되지 않지만, 나중에 CDN 등이 앞단에 추가되면 이 설정도 다시 확인해야 한다.

- [ ] **NestJS(`main.ts`)의 `app.set('trust proxy', 1)`이 배포 환경에 적용되어 있다.** (코드에는 이미 반영되어 있음 — 실제로 서버에 배포된 빌드에 포함됐는지만 확인) `1`은 "가장 가까운 프록시 hop(Nginx) 하나만 신뢰"를 의미한다. Nginx와 NestJS 사이에 다른 프록시(로드밸런서 등)가 추가되면 이 숫자를 재검토해야 한다.

- [ ] **NestJS 포트(기본 3001)가 인터넷에 직접 노출되지 않는다.**
  `trust proxy`가 켜진 상태에서 NestJS 포트가 외부에 그대로 열려 있으면, 공격자가 `X-Forwarded-For` 헤더를 요청마다 다른 값으로 바꿔 보내는 것만으로 로그인 rate limit을 완전히 우회할 수 있다(Nginx를 거치지 않고 직접 요청하면서 신뢰할 수 없는 IP를 자칭할 수 있기 때문).
  - 확인 방법: 서버 외부에서 `curl http://<서버 공인 IP>:3001/...`을 호출했을 때 응답이 없어야 한다.
  - 조치: 방화벽(Security List/iptables)에서 3001 포트를 외부에 막거나, NestJS를 `127.0.0.1`에만 바인딩한다.

# 1-1. Socket.IO WebSocket Upgrade

배경: `003_백엔드2_운영실시간.md` §36에서 `/socket.io/*`를 NestJS Socket.IO로 라우팅하기로 확정했지만, 그 결정을 실제로 동작시키려면 Nginx가 HTTP 요청을 WebSocket으로 업그레이드해서 전달해야 한다. 이 설정이 빠지면 Socket.IO가 매 요청마다 새로 연결하는 HTTP long-polling으로만 동작해 실시간성이 떨어지고 서버 자원도 더 사용한다.

- [ ] **Nginx `/socket.io/` location에 업그레이드 헤더를 설정한다.**

  ```nginx
  location /socket.io/ {
      proxy_pass http://127.0.0.1:3001;
      proxy_http_version 1.1;
      proxy_set_header Upgrade $http_upgrade;
      proxy_set_header Connection "upgrade";
      proxy_set_header Host $host;
      proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
      proxy_set_header X-Forwarded-Proto $scheme;
  }
  ```

- [ ] 배포 환경에서 브라우저 개발자도구(Network 탭)로 Socket.IO 연결이 `101 Switching Protocols`(WebSocket)로 업그레이드되는지 확인한다. 업그레이드가 안 되면 폴링으로 자동 fallback되어 기능은 동작하지만, 장시간 운영 시 지연/서버 부하가 늘어나므로 원인(Nginx 설정 누락)을 먼저 확인한다.
- [ ] Nginx `proxy_read_timeout`이 Socket.IO 기본 핑/타임아웃 주기보다 짧게 설정되어 있지 않은지 확인한다(짧으면 정상 연결도 중간에 끊긴다).

# 2. 로그인 Rate Limit 실동작 검증

- [ ] 서로 다른 클라이언트(예: 사무실 Wi-Fi와 모바일 핫스팟처럼 IP가 다른 두 네트워크)에서 각각 로그인을 반복 시도했을 때, 한쪽이 `429`를 받아도 다른 쪽은 영향받지 않는지 확인한다.
- [ ] 같은 클라이언트가 60초 안에 10회를 초과해 시도하면 실제로 `429 TOO_MANY_REQUESTS`가 오는지 확인한다.
  - 만약 정상적인 사용자가 소수의 재시도만으로도 쉽게 차단된다면, §1의 `X-Forwarded-For` 설정이 누락되어 전체 사용자가 Nginx의 IP 하나로 묶여 집계되고 있는 것일 수 있다 — 이 경우 §1을 먼저 확인한다.
- [ ] `429` 응답 body가 `{"code":"TOO_MANY_REQUESTS","message":"요청이 너무 많습니다. 잠시 후 다시 시도해 주세요."}` 형태로 오는지 확인한다.

# 3. 환경변수

- [ ] `ADMIN_JWT_SECRET`이 32자 이상의 충분히 무작위한 값인지 확인한다(`openssl rand -base64 48` 등으로 생성, `001_백엔드_공통.md` §46 참고). 짧거나 예측 가능한 값이면 앱이 아예 시작되지 않는다(`env.validation.ts`).
- [ ] `COOKIE_SECURE=true`, `COOKIE_SAME_SITE=lax`(또는 `strict`)로 설정되어 있는지 확인한다. HTTPS 배포이므로 `COOKIE_SECURE=false`로 두면 안 된다.
- [ ] `NODE_ENV=production`인지 확인한다.
- [ ] 로그인 후 `Set-Cookie`의 `Max-Age`가 `43200`(12시간, 확정 2026-09-20)인지, 그리고 만료 후 REST `401 ADMIN_UNAUTHORIZED`와 기존 관리자 Socket 종료가 실제로 동작하는지 확인한다.

# 3-1. 공유 기기(iPad 등) 운영 수칙

- [ ] 관리자 JWT 유효기간이 12시간으로 길어진 만큼(확정, 2026-09-20), 아이패드 등 여러 관리자가 함께 쓰는 기기는 운영 종료·인수인계 시 반드시 명시적으로 로그아웃한다.
- [ ] 배포 직후 기존 로그인 세션(이 배포 이전에 발급된 JWT)은 `jti`(로그인 세션 식별자)가 없어, 남은 유효기간(최대 12시간) 동안은 로그아웃 시 계정(adminId) 단위로 종료될 수 있다(§10, 세션 단위 매칭 도입 이전 토큰과의 하위 호환). 배포 후 전 관리자 1회 재로그인을 권장한다.

# 5. 메뉴 사진 & CDN (확정, 2026-09-19)

**배경:** Oracle Cloud 서버가 유럽 리전이라, 이미지를 원본 서버에서 직접 서빙하면 실제 사용자(한국 축제 현장) 기준으로 매 요청마다 유럽까지 왕복하는 지연이 생긴다.

**결정:**

```text
이미지 저장 위치: 서버(로컬 디스크). S3 등 별도 오브젝트 스토리지는 쓰지 않는다.

원본이 유럽 리전이어도 체감 속도를 확보하기 위해 Nginx 앞단에 CDN(Cloudflare 등 무료
플랜)을 추가한다. 이미지처럼 자주 안 바뀌는 정적 리소스는 CDN 엣지 캐시에 적합하다.

이미지 응답에는 Cache-Control(public, max-age 등) 헤더를 설정해 CDN/브라우저 캐시가
정상 동작하게 한다.
```

**현재 구현 범위가 아님 (의도적 보류):**

```text
menus 테이블에 이미지 컬럼(image_url 등) 없음
이미지 업로드 API 없음
정적 파일 서빙 라우트 없음
CDN(Cloudflare) 실제 설정 없음
```

이 항목들은 이번 Menu 도메인 구현(가격/품절 관리)의 스코프에 포함하지 않았다. 실제 메뉴 사진 파일은 Step 11(Oracle 배포) 진행 시점에 서버에 올리기로 했고, 그때 이미지 저장/서빙 구현과 CDN 설정을 함께 진행한다.

**Step 11 착수 시 할 일:**

- [ ] `menus` 테이블에 이미지 경로 컬럼 추가 마이그레이션 작성 (컬럼명/타입은 그때 확정)
- [ ] 이미지 파일을 서버 로컬 디스크에 저장하고 정적 파일로 서빙하는 라우트 구현
- [ ] 관리자가 메뉴 사진을 올리는 방법 확정 (업로드 API vs 배포 시 수동 배치)
- [ ] Nginx 앞단에 Cloudflare(또는 동급 CDN) 연결
- [ ] 이미지 응답에 `Cache-Control` 헤더 적용 확인
- [ ] 실제 한국 현지 네트워크에서 이미지 로딩 속도 체감 테스트
