# 2026 ANU Festival 주문 서비스 — 전체 흐름 요약

> 이 문서는 프론트엔드 / 백엔드 개발자가 프로젝트 전체 흐름을 빠르게 이해하기 위한 요약 문서입니다.
>
> 세부 API, DB 구조, 인증 방식 등 구체적인 구현 내용은 각 개발 계획서를 참고합니다.

---

# 1. 우리가 만드는 서비스

학교 축제 부스에서 손님이 **QR 코드를 스캔하여 메뉴를 주문**하고,
관리자가 별도의 관리자 페이지에서 주문을 확인하고 처리하는 웹 서비스입니다.

전체적인 흐름은 다음과 같습니다.

```text
┌──────────────┐
│   👤 손님     │
│    휴대폰     │
└──────┬───────┘
       │
       │ QR 접속
       ▼
┌──────────────┐
│  고객 주문 웹 │
└──────┬───────┘
       │
       │ 주문
       ▼
┌──────────────┐
│    백엔드     │
│ 주문 저장/관리 │
└──────┬───────┘
       │
       │ 새 주문
       ▼
┌──────────────┐
│  🧑‍🍳 관리자   │
│  관리자 페이지 │
└──────┬───────┘
       │
       │ 입금 확인 / 조리 상태 변경
       ▼
┌──────────────┐
│    백엔드     │
└──────┬───────┘
       │
       │ 변경된 상태
       ▼
┌──────────────┐
│   👤 손님     │
│ 주문 상태 확인 │
└──────────────┘
```

쉽게 말하면,

**손님이 주문 → 서버가 저장 → 관리자가 주문 처리 → 손님이 주문 상태 확인**

의 흐름입니다.

---

# 2. 고객은 회원가입하지 않는다

고객은 별도의 회원가입이나 로그인을 하지 않습니다.

또한 고객을 특정하기 위한 `guest_id` 쿠키도 사용하지 않는 방향으로 진행합니다.

즉 고객 영역은 기본적으로 **Stateless**하게 구성합니다.

```text
회원가입 ❌
고객 로그인 ❌
guest_id 쿠키 ❌

주문 자체가 독립적으로 존재
```

한 휴대폰을 여러 사람이 사용하더라도 특정 고객 계정이나 쿠키에 주문이 묶이지 않습니다.

예를 들어 한 휴대폰에서 다음과 같이 주문해도 각각 별도의 주문으로 처리합니다.

```text
한 휴대폰

├─ 철수 주문 → 0918-0001
├─ 영희 주문 → 0918-0002
└─ 민수 주문 → 0918-0003
```

# 3. QR을 처음 스캔했을 때

QR 코드를 스캔하면 고객용 메인 화면으로 이동합니다.

```text
┌─────────────────────────┐
│                         │
│      🎪 축제 주문        │
│                         │
│   ┌─────────────────┐   │
│   │    주문하기      │   │
│   └─────────────────┘   │
│                         │
│   ┌─────────────────┐   │
│   │    주문 확인     │   │
│   └─────────────────┘   │
│                         │
└─────────────────────────┘
```

- **주문하기**: 새로운 주문 생성
- **주문 확인**: 기존에 주문한 내용을 다시 확인

---

# 4. 주문하기

고객은 주문할 때 기본적으로 다음 정보를 입력합니다.

- 이름
- 전화번호
- 메뉴
- 수량

예상 화면은 다음과 같습니다.

```text
┌─────────────────────────┐
│       🍴 주문하기        │
│                         │
│ 이름                    │
│ ┌─────────────────────┐ │
│ │ 홍길동              │ │
│ └─────────────────────┘ │
│                         │
│ 전화번호                │
│ ┌─────────────────────┐ │
│ │ 010-1234-5678       │ │
│ └─────────────────────┘ │
│                         │
│ 아망추          3,500원 │
│             [ -  2  + ] │
│                         │
│ 크로플          4,000원 │
│             [ -  1  + ] │
│                         │
│ ─────────────────────── │
│ 총 금액         11,000원 │
│                         │
│      [ 주문하기 ]        │
└─────────────────────────┘
```

전화번호는 고객의 신원을 확인하기 위한 계정 개념이 아니라,
**주문 처리 중 필요한 경우 고객에게 연락하기 위한 정보**입니다.

예를 들어 다음과 같은 상황에서 사용할 수 있습니다.

- 주문이 완료되어 수령이 필요한 경우
- 주문에 문제가 발생한 경우
- 장시간 수령하지 않는 경우

상황에 따라 **문자 또는 전화로 고객에게 연락**할 수 있습니다.

# 5. 주문 생성

고객이 주문하기 버튼을 누르면 프론트엔드가 주문 내용을 백엔드로 전달합니다.

```text
고객

이름
전화번호
메뉴
수량
   │
   ▼
┌───────────────┐
│   프론트엔드   │
└───────┬───────┘
        │
        │ 주문 요청
        ▼
┌───────────────┐
│    백엔드      │
│               │
│ 메뉴 확인      │
│ 가격 확인      │
│ 품절 확인      │
│ 주문 저장      │
└───────┬───────┘
        │
        ▼
     주문 완료
```

프론트엔드 화면에 표시된 가격을 그대로 믿고 저장하지 않습니다.

백엔드에서 현재 메뉴의

- 실제 가격
- 판매 가능 여부

를 다시 확인하고 최종 주문 금액을 계산합니다.

# 6. 주문번호 발급

주문이 성공하면 고객에게 주문번호를 발급합니다.

예:

```text
0918-0001
0918-0002
0918-0003
...
```

앞의 `0918`은 날짜,
뒤의 번호는 해당 날짜의 주문 순서입니다.

주문 완료 화면은 다음과 같은 형태입니다.

```text
┌─────────────────────────┐
│       주문 완료!         │
│                         │
│        주문번호          │
│                         │
│       0918-0042          │
│                         │
│ ─────────────────────── │
│ 입금 계좌                │
│ 신한 123-456-789         │
│ 예금주 : OOO             │
│                         │
│ 결제금액       11,000원  │
│                         │
│ 현재 상태                │
│       💰 입금 대기        │
│                         │
│    [ 주문 상태 확인 ]     │
└─────────────────────────┘
```

---

# 7. 결제 방식

현재 MVP에서는 별도의 카드결제 시스템을 사용하지 않습니다.

고객이 화면에 표시된 계좌로 직접 계좌이체합니다.

```text
주문 생성
   │
   ▼
계좌번호 표시
   │
   ▼
고객 계좌이체
   │
   ▼
관리자가 실제 입금 확인
   │
   ▼
주문 접수
```

즉,

**고객이 송금했다고 자동으로 결제가 완료되는 구조가 아닙니다.**

관리자가 직접 입금 내역을 확인한 후 관리자 페이지에서 **입금 확인** 처리를 합니다.

---

# 8. 관리자 주문 확인

관리자는 고객과 별도의 관리자 페이지를 사용합니다.

```text
┌────────────────────────────────────────────┐
│ 관리자 페이지                              │
├─────────┬──────────────────────────────────┤
│ 주문관리 │  🔔 새로운 주문                  │
│ 메뉴관리 │                                  │
│ 매출     │  0918-0042   홍길동   11,000원  │
│ 계좌설정 │  아망추 ×2 / 크로플 ×1           │
│          │                                  │
│          │  상태 : 입금 대기                 │
│          │                                  │
│          │       [ 입금 확인 ]               │
│          │       [ 주문 취소 ]               │
└─────────┴──────────────────────────────────┘
```

관리자는 주문 페이지에서 새로 들어온 주문을 확인하고 처리합니다.

---

# 9. 주문 상태 흐름

기본적인 주문 상태는 다음과 같습니다.

```text
┌─────────────┐
│  💰 입금대기 │
└──────┬──────┘
       │
       │ 관리자 입금 확인
       ▼
┌─────────────┐
│  ✅ 주문접수 │
└──────┬──────┘
       │
       │ 조리 시작
       ▼
┌─────────────┐
│   🍳 조리중  │
└──────┬──────┘
       │
       │ 조리 완료
       ▼
┌─────────────┐
│  🔔 조리완료 │
└──────┬──────┘
       │
       │ 고객 수령
       ▼
┌─────────────┐
│  ✔ 수령완료 │
└─────────────┘
```

입금 전에는 주문 취소도 가능합니다.

```text
입금대기 ─────────→ 주문취소
```

결제 이후에는 환불 기능도 제공할 예정입니다.

단, 전액/부분 환불이나 환불 시 매출 계산 등 세부 정책은 별도로 확정합니다.

---

# 10. 고객 주문 상태 화면

고객은 자신의 주문이 현재 어느 단계인지 확인할 수 있습니다.

예를 들어 다음과 같은 화면입니다.

```text
┌─────────────────────────┐
│ 주문번호 0918-0042      │
│                         │
│ 아망추 ×2               │
│ 크로플 ×1               │
│                         │
│ 총 11,000원              │
│                         │
│ ●──────●──────●──────○  │
│ 입금확인  접수    조리중  완료 │
│                         │
│     현재 조리 중입니다.   │
└─────────────────────────┘
```

관리자가 주문 상태를 변경하면 고객도 변경된 주문 상태를 확인할 수 있도록 합니다.

---

# 11. 주문 완료 시 고객 연락

조리가 완료되면 주문 상태를 **조리 완료**로 변경합니다.

```text
관리자

[ 조리 완료 ]
      │
      ▼
주문 상태 변경
      │
      ├──────────────→ 고객 웹에서 상태 확인
      │
      └──────────────→ 필요 시 문자 / 전화 연락
```

주문할 때 입력받은 전화번호를 이용하여
고객에게 직접 연락할 수 있습니다.

예:

```text
"0918-0042 주문 조리가 완료되었습니다.
부스로 방문하여 수령해주세요."
```

문자를 시스템에서 자동 발송할지,
관리자가 직접 문자/전화를 할지는 구현 범위에 따라 결정할 수 있습니다.

---

# 12. 기존 주문 다시 확인

고객이 웹페이지를 나갔다가 다시 접속할 수도 있습니다.

이 경우 **주문 확인** 화면에서 기존 주문을 조회합니다.

기본 조회 정보는 다음과 같이 구성합니다.

```text
┌─────────────────────────┐
│       주문 확인          │
│                         │
│ 이름                    │
│ ┌─────────────────────┐ │
│ │ 홍길동              │ │
│ └─────────────────────┘ │
│                         │
│ 주문번호                │
│ ┌─────────────────────┐ │
│ │ 0918-0042           │ │
│ └─────────────────────┘ │
│                         │
│       [ 조회하기 ]       │
└─────────────────────────┘
```

```text
이름 + 주문번호
       │
       ▼
백엔드에서 일치하는 주문 확인
       │
       ▼
해당 주문 상태 표시
```

고객용 `guest_id` 쿠키는 사용하지 않기 때문에
**특정 휴대폰 자체를 한 명의 고객으로 취급하지 않습니다.**

따라서 같은 휴대폰에서 여러 사람이 주문해도 각각 독립적인 주문으로 처리할 수 있습니다.

# 13. 관리자 페이지

관리자 기능은 크게 다음 네 가지입니다.

```text
┌──────────────────────────────────────┐
│              관리자                  │
├──────────────────────────────────────┤
│                                      │
│  📋 주문 관리                         │
│  입금 확인 / 조리중 / 완료 / 취소     │
│                                      │
│  🍴 메뉴 관리                         │
│  가격 변경 / 품절 설정                │
│                                      │
│  💰 매출                              │
│  판매금액 / 판매내역 확인             │
│                                      │
│  🏦 계좌 설정                         │
│  고객에게 표시할 입금 계좌 변경        │
│                                      │
└──────────────────────────────────────┘
```

## 주문 관리

관리자가 가장 많이 사용하는 화면입니다.

```text
새 주문
   ↓
입금 확인
   ↓
주문 접수
   ↓
조리 시작
   ↓
조리 완료
   ↓
고객 수령
   ↓
수령 완료
```

## 메뉴 관리

축제에서 판매할 메뉴는 미리 정해져 있습니다.

따라서 복잡한 메뉴 추가/삭제 기능보다는

- 가격 변경
- 품절 여부 변경

위주로 관리합니다.

```text
아망추             3,500원    판매중
아이스크림 크로플   4,000원    판매중
오레오 크로플       4,500원    품절
```

## 매출

입금이 확인된 주문을 기준으로 판매 현황과 매출을 확인합니다.

민감한 정보이기 때문에 매출 화면에 접근할 때 관리자 비밀번호를 다시 확인하는 방식으로 구성합니다.

## 계좌 설정

고객 주문 완료 화면에 표시할 입금 계좌를 관리합니다.

```text
은행
계좌번호
예금주
```

관리자가 계좌 정보를 변경하면 이후 고객에게 현재 설정된 계좌가 표시됩니다.

# 14. 프론트엔드 / 백엔드 / DB 관계

전체 구조를 아주 단순하게 표현하면 다음과 같습니다.

```text
                 👤 고객
                   │
                   ▼
          ┌────────────────┐
          │   프론트엔드    │
          │                │
          │ 고객 주문 화면  │
          │ 주문 상태 화면  │
          │ 관리자 화면     │
          └───────┬────────┘
                  │
                  │ 요청 / 응답
                  ▼
          ┌────────────────┐
          │     백엔드      │
          │                │
          │ 주문 처리       │
          │ 관리자 기능     │
          │ 상태 관리       │
          └───────┬────────┘
                  │
                  │ 저장 / 조회
                  ▼
          ┌────────────────┐
          │   PostgreSQL   │
          │                │
          │ 주문           │
          │ 메뉴           │
          │ 관리자         │
          │ 매출 관련 정보  │
          └────────────────┘
```

### 프론트엔드

사용자와 관리자가 실제로 보는 화면을 담당합니다.

예:

- 메뉴 화면
- 주문 화면
- 주문 상태 화면
- 주문 조회 화면
- 관리자 주문 화면
- 메뉴 관리 화면
- 매출 화면
- 계좌 설정 화면

### 백엔드

프론트엔드에서 들어온 요청을 실제로 처리합니다.

예:

- 주문 생성
- 가격 확인
- 주문번호 생성
- 주문 상태 변경
- 입금 확인
- 취소 / 환불
- 관리자 로그인
- 메뉴 관리
- 매출 계산
- 계좌 설정

### DB

서비스에서 계속 보관해야 하는 데이터를 저장합니다.

예:

- 주문
- 주문한 메뉴
- 주문 상태 기록
- 메뉴
- 관리자
- 환불 정보
- 현재 입금 계좌

# 15. 개발 역할 분담

현재 프로젝트는 프론트엔드 1명, 백엔드 2명으로 개발합니다.

```text
┌───────────────────────────────────────┐
│               프로젝트                │
├─────────────┬─────────────┬───────────┤
│ 프론트엔드  │  백엔드 1   │ 백엔드 2  │
├─────────────┼─────────────┼───────────┤
│ 고객 화면   │ 주문 생성   │ 관리자로그인│
│ 관리자 화면 │ 주문 조회   │ 메뉴 관리  │
│ 주문 UI     │ 주문번호    │ 계좌 설정  │
│ 상태 UI     │ 입금 확인   │ 매출       │
│ 조회 UI     │ 상태 변경   │ 실시간 전달│
│             │ 취소/환불   │ 서버 배포  │
└─────────────┴─────────────┴───────────┘
```

각자 담당 영역은 나뉘어 있지만 실제 서비스에서는 모두 연결됩니다.

예를 들어 주문 하나가 발생하면:

```text
프론트엔드
"아망추 2개 주문"
       │
       ▼
백엔드 1
주문 생성 + DB 저장
       │
       ▼
백엔드 2
새 주문 발생을 관리자에게 전달
       │
       ▼
프론트엔드
관리자 주문 화면에 표시
       │
       ▼
관리자
입금 확인 / 조리 상태 변경
       │
       ▼
백엔드
주문 상태 변경
       │
       ▼
프론트엔드
고객에게 현재 상태 표시
```

따라서 각자 자기 기능만 보는 것이 아니라
**주문 하나가 처음부터 끝까지 어떻게 흐르는지 같이 이해하는 것이 중요합니다.**

# 17. 현재 확정하지 않은 부분

아래 내용은 개발하면서 추가 협의가 필요합니다.

### 고객 주문 유지 방식

고객용 `guest_id` 쿠키는 제거하고 Stateless 구조로 진행합니다.

다만 주문 직후 페이지 새로고침이나 재접속 시 사용자가 다시 정보를 입력하지 않도록 할지,
브라우저에 최근 주문 정보를 임시 저장할지 등의 세부 UX는 추가 결정이 필요합니다.

### 고객 주문 상태 갱신 방식

관리자 페이지에는 실시간 주문 반영이 필요합니다.

고객 주문 상태 화면까지 실시간 연결을 사용할지,
일정 시간마다 서버에서 최신 상태를 확인하는 방식으로 구성할지는 추가 결정이 필요합니다.

### 문자 발송

전화번호 입력은 주문 시 받습니다.

다만 조리 완료 시

- 관리자가 직접 문자 발송
- 관리자가 직접 전화
- 시스템에서 문자 자동 발송

중 어디까지 구현할지는 추가 결정이 필요합니다.

### 환불

환불 기능 자체는 필요하지만 다음 내용은 추가 협의가 필요합니다.

- 전액 환불 / 부분 환불
- 환불 이후 주문 상태 표현
- 환불된 금액의 매출 반영 방식
- 이미 조리가 시작된 주문의 처리

# 18. 핵심만 다시 정리

```text
고객
│
├─ QR 접속
├─ 이름 + 전화번호 입력
├─ 메뉴 선택
├─ 주문
├─ 주문번호 발급
├─ 계좌이체
└─ 주문 상태 확인
        │
        ▼
      백엔드
        │
        ▼
      관리자
        │
├─ 입금 확인
├─ 주문 접수
├─ 조리 시작
├─ 조리 완료
├─ 필요 시 문자/전화
└─ 수령 완료
        │
        ▼
고객 화면에 상태 반영
```

고객은 회원가입이나 로그인을 하지 않으며,
특정 휴대폰을 한 명의 고객으로 취급하지 않습니다.

**각 주문은 독립적으로 관리하고, 기존 주문은 이름 + 주문번호를 이용해 다시 조회합니다.**

전화번호는 고객 계정이나 주문 조회용 신원 정보가 아니라,
**주문 완료 또는 문제가 발생했을 때 고객에게 연락하기 위한 용도**로 사용합니다.
